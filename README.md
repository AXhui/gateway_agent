# Modulor · 基于飞书多维表格 + 机器人的 UED 组件 Agent 体系：PRD 一键生成可交互 Demo 与 Figma 设计稿，可量化质量校验，多产品线复用

> 不"画"原型，而是从线上产品**同源的组件库里装配**原型。
> 生成物是一份内联全部样式的单文件 HTML，可直接交付前端，也可直接给客户演示。

---

## 〇、需求背景与文档目标

**总目标**：把线上平台**已有的组件**沉淀为一套**组件 Skill**，供不同平台（工作台 / 飞书 / 各 Agent）统一调用，从而"一句话"装配出与线上版本**还原度 100%** 的业务页面。

**组件搭建规则（三层递进）**：

1. **基础组件 Skill**（设计令牌 + 基础组件）—— 从线上组件文档原样抽取，只引用令牌、不写裸值，这是还原度可计算的前提；
2. **业务组件封装** —— 声明 `atoms` 依赖序列 + `render` 骨架，调用基础组件拼出业务块，零新增样式；
3. **Demo 拼装成页面**（模块 + 模板装配知识）—— 按一句话识别出的形态与动作，把业务组件有序装配成完整页面。

> 本文件后续一切内容 —— 组件库 4 层架构、Agent 链路、还原度算法、目录结构 —— 都围绕这一总目标与搭建规则展开，不作它途。

---

## 一、要解决的问题

产品线上的真实页面和 AI 生成的"演示稿"之间，长期存在一道还原度鸿沟：

| 传统做法 | 结果 |
|---|---|
| AI 自由发挥写 HTML/CSS | 视觉像，但和线上组件对不上，前端无法复用 |
| 设计稿切图 + 手写 demo | 还原度高，但一个页面要 1~2 天，改一版再等一天 |
| 低代码拖拽 | 产物脱离组件库，无法回到工程 |

本项目的判断是：**还原度问题不是"生成能力"问题，而是"约束"问题**。
只要把生成过程严格约束在「设计令牌 → 基础组件 → 业务组件 → 模块/模板装配知识」这四层已封装资产之内，
生成的页面在结构上就必然与线上同源 —— 还原度因此从"形容词"变成了"可计算的数"。

## 二、架构总览

一条 PRD 从飞书文档到「可交互 Demo + 可编辑 Figma 设计稿」的完整流水线：

```
┌─────────────────────────────────────────────────────────────┐
│  需求层（产品经理）                                           │
│  PRD 飞书文档                                                 │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
              ┌──────────────────────────────┐
              │  A0 PRD 三角色拆解 Agent       │
              │  → UED / DEV / 测试 三份视角文档 │
              └──────┬──────────┬──────────┬───┘
                     ▼          ▼          ▼
              UED 链路      DEV 链路      测试链路
              (A1–A8)      (D1–D5)      (T1–T4)
                     │
                     ▼
              ┌──────────────────────────────┐
              │  组件库（4 层架构）             │
              │  基础组件 · 业务组件 · 治理规则 · Agent规则 │
              └──────┬───────────────────────┘
                     ▼
              可交互 Demo（HTML）
                     ▼
              还原度校验（5 维度）
                     ▼
              质量数据记录（多维表格）+ 自动化反馈（机器人）
                     ▼
              A8 Figma 转换 + UED 审核补充
              → 可编辑 Figma 设计稿 + UED 审核报告 + 补充项清单
                     │
                     └──→ 组件优化反馈（闭环迭代）
```

### 组件库 4 层架构

| 层 | 目录 | 定位 | 规模 |
|---|---|---|---|
| **基础组件** | `.claude/skills/base/` + `.claude/tokens/` | 设计令牌 + 基础组件 Skill（唯一真源 · 只读） | 152 令牌 + 63 组件 |
| **业务组件** | `.claude/skills/business/` | 仅组合基础组件，零新增样式 | 19 个 |
| **治理规则** | `.claude/rules/` | 封装 / 版本 / 命名 / 文档 / 发布 + 业务补充 | 6 份 |
| **Agent规则** | `.claude/agents/` + `.claude/knowledge/` | Agent 定义 + 需求→组件映射知识（含 M_*/T_* 模块/模板装配知识） | 18 agent（A0 + A1–A8 + D1–D5 + T1–T4）+ K_* |

### Agent 链路

| 链 | 步数 | 视角 | 起点 → 终点 |
|---|---|---|---|
| **A0 拆解** | 1 | 编排入口 | PRD 飞书文档 → UED/DEV/测试 三份视角文档 |
| **UED 链路** | A1–A8 | 设计/视觉 | UED 文档 → 可交互 Demo → Figma 设计稿 + UED 审核报告 |
| **DEV 链路** | D1–D5 | 开发 | DEV 文档 → page.json 契约 |
| **测试链路** | T1–T4 | 测试 | 测试文档 → 还原度校验 + 质量数据记录 |

> 模块（`M_*`，12 个）与模板（`T_*`，11 个）作为**页面装配知识**归入 Agent规则层，由 UED 链路的「模块装配规划」步骤消费。4 层里不再单列模块/模板。

**关键约束（由校验器强制）**

1. 基础/业务组件任何一处出现硬编码色值即判定违规 —— 必须引用设计令牌；
2. 生成稿里出现的每一个 class 都必须能在 4 层资产库中溯源；
3. 业务组件声明的每一个基础组件依赖都必须是"已封装"状态；
4. 装配计划里的每一个模块都必须在生成稿中落地；
5. 五轴交互（hover/active/keyboard/loading/error）在 demo 中可测、可断言。

## 三、两种生成模式

### 模式 A · 模块匹配复用
适合"线上已有类似页面，快速出一版 demo"。

```
一句话 → 意图解析 → 模板打分 → 模块装配 → 渲染 → 还原度校验
```

规划器不是"整体套模板"，而是**先选模板、再按识别出的形态/动作做模块增删**：
同样一句"列表"，加了"弹窗"就会多出任务弹窗区块，加了"图表"就会多出遥测区块 ——
一句话的微小差异会产出结构不同的页面。

### 模式 B · 新业务自主生成（Learner Agent）
适合"资产库里根本没有这块业务"。

```
一句话 → 意图解析 → 实体判定 → 检索相似业务组件 → 抽取搭建逻辑
       → 字段迁移 → 生成并注册新业务组件 → 装配成页 → 还原度校验
```

Agent 学到的不是样式，而是**搭建逻辑**：

- 搭建逻辑 = 业务组件声明的 `atoms` 依赖序列 + `render` 骨架。
  样式细节由 L1 令牌统一保证，所以新组件**零新增样式行**、天然继承线上视觉规范。
- 字段迁移 = 从未命中实体时，借用最相似实体的字段结构（依据：最相似业务组件的实体归属），
  改名后注册为新实体，因此新业务页面不会出现"结构空壳"。
- 生成物全部注册回资产库，**下次即可被规划器直接复用**，形成正循环。

## 四、还原度是怎么算的

「100%」不是宣传语，而是五条规则加权后的结果（工作台右侧"还原度"页可逐条查看证据）：

| 规则 | 权重 | 含义 |
|---|---|---|
| R1 令牌合规率 | 25 | 组件层与生成稿中不得出现硬编码色值，必须引用设计令牌 |
| R2 组件溯源率 | 25 | 生成稿每一个 class 都必须能在资产库中溯源 |
| R3 依赖闭环率 | 20 | 业务组件的每个基础组件依赖都必须是已封装状态 |
| R4 结构覆盖率 | 15 | 装配计划中每个模块都必须在生成稿中落地 |
| R5 交互完备度 | 15 | 五轴交互（hover/active/keyboard/loading/error）在 demo 中可测、可断言 |

当前样例实测：**R1 693 项引用 0 异常 / R2 92 个 class 全部可溯源 / R3 / R4 / R5 全通过 → 100**。
校验由 A5 agent 按上述五维规则执行（证据落 `05_release/REQ-###/validation.md`）。

## 六、渲染链路（工作台已移除）

页面产出走 **agent 链路**（A1 规划 → A2 匹配 → A3 page.json → A4 渲染），不再有本地工作台：

- 组件运行时真源：`library/*.css`（样式）+ `assets/js/registry-*.js`（render 骨架），A4 渲染时**内联**进 `05_release/REQ-###/demo.html`（单文件、零依赖）。
- 临时核实页落 `output/`（见 `.claude/rules/output.md`）。

## 七、与"让 AI 直接写页面"的本质区别

| 维度 | AI 直接写 HTML | Modulor |
|---|---|---|
| 视觉来源 | 模型自由发挥 | 与线上同源的令牌 + 组件实现 |
| 还原度 | 主观评价 | 5 条规则可计算、可回归 |
| 产物去向 | 一次性演示稿 | 结构可回到工程：模块/组件/令牌三层可溯源 |
| 新业务扩展 | 每次从零生成 | 复用搭建逻辑，零新增样式，且沉淀回资产库 |
| 交付形态 | 需要前端重做 | 单文件 HTML，含真实组件结构 |

## 八、已知边界

- 基础组件 62 个已封装、在册 63 个（见 `_index.json`）；未封装的在资产库中标记为"在册待封装"，规划器不会引用它们（由 R3 保证）。
- 意图解析为词典驱动的确定性实现，不依赖大模型接口，因此结果可复现、可回归；代价是对词典外的新词需要走 Learner 铸造路径。
- 生成稿中的图表为纯内联 SVG（不引第三方图表库），保证零依赖，但交互能力限于静态呈现。
- 生成稿是**可交互外观的静态稿**：Tab 切换、下拉选择等原生控件可操作，业务行为（分页跳转、弹窗开关）需接真实数据后由工程侧补齐。
