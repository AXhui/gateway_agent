# Modulor · 一句话生成 100% 还原的业务页面 Demo

> 不"画"原型，而是从线上产品**同源的组件库里装配**原型。
> 生成物是一份内联全部样式的单文件 HTML，可直接交付前端，也可直接给客户演示。

---

## 一、要解决的问题

产品线上的真实页面和 AI 生成的"演示稿"之间，长期存在一道还原度鸿沟：

| 传统做法 | 结果 |
|---|---|
| AI 自由发挥写 HTML/CSS | 视觉像，但和线上组件对不上，前端无法复用 |
| 设计稿切图 + 手写 demo | 还原度高，但一个页面要 1~2 天，改一版再等一天 |
| 低代码拖拽 | 产物脱离组件库，无法回到工程 |

本项目的判断是：**还原度问题不是"生成能力"问题，而是"约束"问题**。
只要把生成过程严格约束在「设计令牌 → 基础组件 → 业务组件 → 模块 → 页面模板」这五层已封装资产之内，
生成的页面在结构上就必然与线上同源 —— 还原度因此从"形容词"变成了"可计算的数"。

## 二、五层架构

```
L5  页面模板  templates   11 个      所属页面骨架：概览 / 列表 / 详情 / 告警 / 升级 / 权限 …
      ↑ 有序组合
L4  页面模块  modules     12 个      区块级装配：指标区、列表区、遥测区、拓扑区 …
      ↑ 1~N 个业务组件 + 区块标题 + 栅格
L3  业务组件  business    14 个      设备列表、告警规则表单、固件升级弹窗、网络拓扑 …
      ↑ 只调用基础组件，不写视觉常量
L2  基础组件  atoms       64 个（已封装 48）Button / Table / Form / Modal / Drawer / Timeline …
      ↑ 只引用令牌
L1  设计令牌  tokens      161 条     从线上组件文档原样抽取，唯一真源
```

**关键约束（由校验器强制）**

1. L2/L3 任何一处出现硬编码色值即判定违规 —— 必须引用 L1 令牌；
2. 生成稿里出现的每一个 class 都必须能在这五层资产库中溯源；
3. 业务组件声明的每一个基础组件依赖都必须是"已封装"状态；
4. 装配计划里的每一个模块都必须在生成稿中落地。

## 三、两种生成模式

### 模式 A · 模块匹配复用
适合"线上已有类似页面，快速出一版 demo"。

```
一句话 → 意图解析 → 模板打分 → 模块装配 → 渲染 → 还原度校验
```

规划器不是"整体套模板"，而是**先选模板、再按识别出的形态/动作做模块增删**：
同样一句"列表"，加了"弹窗"就会多出任务弹窗区块，加了"图表"就会多出遥测区块 ——
一句话的微小差异会产出结构不同的页面。

### 模式 B · 新业务自主生成（Learner Agent）
适合"资产库里根本没有这块业务"。

```
一句话 → 意图解析 → 实体判定 → 检索相似业务组件 → 抽取搭建逻辑
       → 字段迁移 → 生成并注册新业务组件 → 装配成页 → 还原度校验
```

Agent 学到的不是样式，而是**搭建逻辑**：

- 搭建逻辑 = 业务组件声明的 `atoms` 依赖序列 + `render` 骨架。
  样式细节由 L1 令牌统一保证，所以新组件**零新增样式行**、天然继承线上视觉规范。
- 字段迁移 = 从未命中实体时，借用最相似实体的字段结构（依据：最相似业务组件的实体归属），
  改名后注册为新实体，因此新业务页面不会出现"结构空壳"。
- 生成物全部注册回资产库，**下次即可被规划器直接复用**，形成正循环。

## 四、还原度是怎么算的

「100%」不是宣传语，而是四条规则加权后的结果（工作台右侧"还原度"页可逐条查看证据）：

| 规则 | 权重 | 含义 |
|---|---|---|
| R1 令牌合规率 | 30 | 组件层与生成稿中不得出现硬编码色值，必须引用 L1 令牌 |
| R2 组件溯源率 | 30 | 生成稿每一个 class 都必须能在资产库中溯源 |
| R3 依赖闭环率 | 25 | 业务组件的每个基础组件依赖都必须是已封装状态 |
| R4 结构覆盖率 | 15 | 装配计划中每个模块都必须在生成稿中落地 |

当前样例实测：**R1 693 项引用 0 异常 / R2 92 个 class 全部可溯源 / R3 / R4 全通过 → 100**。
校验器非空跑：注入一个硬编码色值和一个未注册 class 后，分数立即降到 99.6 并给出具体证据。

## 五、目录结构

```
.
├── index.html                 工作台（三栏：资产库 / 预览 / 推理链·还原度·代码）
├── README.md
├── library/                   ← 样式真源（改这里）
│   ├── tokens.css                L1 令牌，从线上文档原样抽取
│   ├── base.css                  L2 基础组件
│   └── business.css              L3 业务组件（只做布局编排）
├── assets/
│   ├── css/workbench.css         工作台外壳样式（与产物视觉刻意区分）
│   └── js/
│       ├── registry-base.js       基础组件注册表（含 props / tokens / 交互 skill）
│       ├── registry-entities.js   业务实体词典 + 确定性造数工厂
│       ├── registry-business.js   业务组件（声明 atoms 依赖 + render 骨架）
│       ├── registry-modules.js    页面模块
│       ├── registry-templates.js  页面模板 + 控制台导航
│       ├── library-css.js         样式层打包产物（自动生成，勿手改）
│       ├── engine-parser.js       引擎① 意图解析
│       ├── engine-planner.js      引擎② 装配规划
│       ├── engine-renderer.js     引擎③ 页面渲染
│       ├── engine-validator.js    引擎④ 还原度校验
│       ├── engine-learner.js      引擎⑤ 新业务组件学习生成
│       └── app.js                 界面装配
├── tools/build-css-bundle.py   把 library/*.css 打包成 JS 常量
└── output/                     导出的 demo 落盘位置
```

## 六、运行

直接打开 `index.html` 即可（样式已打包进 JS，**无需起服务、无网络依赖**）。

修改样式后的流程：

```bash
python3 tools/build-css-bundle.py   # library/*.css → assets/js/library-css.js
# 然后刷新页面
```

导出：工作台右上角「导出 HTML」，产出单文件、零外部依赖、可直接浏览器打开的 demo。

## 七、与"让 AI 直接写页面"的本质区别

| 维度 | AI 直接写 HTML | Modulor |
|---|---|---|
| 视觉来源 | 模型自由发挥 | 与线上同源的令牌 + 组件实现 |
| 还原度 | 主观评价 | 4 条规则可计算、可回归 |
| 产物去向 | 一次性演示稿 | 结构可回到工程：模块/组件/令牌三层可溯源 |
| 新业务扩展 | 每次从零生成 | 复用搭建逻辑，零新增样式，且沉淀回资产库 |
| 交付形态 | 需要前端重做 | 单文件 HTML，含真实组件结构 |

## 八、已知边界

- 基础组件 64 个在册、48 个已封装；未封装的在资产库中标记为"在册待封装"，规划器不会引用它们（由 R3 保证）。
- 意图解析为词典驱动的确定性实现，不依赖大模型接口，因此结果可复现、可回归；代价是对词典外的新词需要走 Learner 铸造路径。
- 生成稿中的图表为纯内联 SVG（不引第三方图表库），保证零依赖，但交互能力限于静态呈现。
- 生成稿是**可交互外观的静态稿**：Tab 切换、下拉选择等原生控件可操作，业务行为（分页跳转、弹窗开关）需接真实数据后由工程侧补齐。
