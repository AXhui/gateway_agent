# 协议速查

> 来源：multitech.com/iot-wiki，检索日期 2026-09-03
> 定位：楼宇自控（BACnet）协议族 + 底层传输/消息协议，产品经理/架构师做协议选型与集成时的判断依据。

---

## 一、BACnet 核心（楼宇自控标准）

### BACnet
- **本质**：ASHRAE 定义的楼宇自控标准协议，让不同厂商的 HVAC、照明、门禁、消防设备互相通信。
- **场景**：任何楼宇自动化/楼宇管理（BMS）的跨厂商集成。
- **坑/判据**：选型第一问是「要不要接入现有 BMS」——要则必须 BACnet；BACnet 是「应用层协议」，底层可跑 MS/TP、IP、以太网多种介质，别把协议和介质混为一谈。

### BACnet/IP
- **本质**：BACnet 跑在标准 IP（UDP/以太网/Wi-Fi）上，最现代的 BACnet 传输方式。
- **场景**：企业级、可扩展、可跨子网的楼宇自控部署，无线传感器上云入 BMS。
- **坑/判据**：跨子网广播受限，需要 BBMD 转发；是企业部署首选，但要规划好 VLAN 与 BBMD。

### BACnet MS/TP
- **本质**：BACnet 跑在 RS-485 串行总线上的数据链路层，主从 + 令牌传递仲裁。
- **场景**：HVAC、照明的现场级控制器、存量串行布线系统。
- **坑/判据**：继承老楼布线成本低，但带宽低、距离受限；网关可桥接 MS/TP 与 IP，实现老系统不换控制器就接入新网络。

### BACnet Secure Connect（BACnet/SC）
- **本质**：下一代 BACnet，用 TLS 1.3 加密认证，hub-and-spoke 架构替代传统广播发现。
- **场景**：企业/云连接楼宇自控、需网络隔离与网络安全的合规场景。
- **坑/判据**：传统 BACnet/IP 明文/弱安全，涉公网或合规要求时优先 BACnet/SC；但要确认两端设备都支持 SC。

## 二、BACnet 对象（数据模型）

### BACnet Objects
- **本质**：BACnet 定义的标准数据类型，表示设备、传感器读数、系统状态、控制命令。
- **场景**：所有 BACnet 点（point）的建模基础。
- **坑/判据**：三大基础对象——Analog（连续值如温度）、Binary（两态如开关）、Multi-State（多离散态）；选型/集成时先确认对方把数据建成了哪种对象。

### Multi-State Objects（多态对象）
- **本质**：表示超过两种离散状态的设备/状态，每个状态有定义值和含义。
- **场景**：风机多档、设备运行模式、占用等级等。
- **坑/判据**：别用 Binary 硬凑「多档」——多态对象才语义正确；状态值和含义要在映射时一一对应，否则 BMS 显示错义。

### Schedule / Calendar Objects（日程/日历对象）
- **本质**：Schedule 控制何时执行动作/设定值，Calendar 定义例外（如节假日）。
- **场景**：HVAC 运行计划、照明周期、基于占用的控制。
- **坑/判据**：把「时间驱动的自动化」交给日程对象而非硬编码；结合无线传感器可实现「按实际环境自适应排程」而非静态假设。

### Trend Log（趋势日志）
- **本质**：采集并存储历史时序数据的 BACnet 对象。
- **场景**：性能分析、诊断、能效验证、合规留痕。
- **坑/判据**：趋势数据是节能验证和 FDD（故障诊断）的基础；选型时确认设备是否支持本地缓存趋势，避免网络抖动丢数。

## 三、BACnet 服务与一致性

### BACnet Services
- **本质**：标准化的通信动作——访问控制、命令、发现。
- **场景**：设备间数据交换与互操作的基础。
- **坑/判据**：核心服务三件套：ReadProperty / WriteProperty（读写值）、SubscribeCOV（订阅变化）、Who-Is / I-Am（发现）；集成前看对方 PICS 支持哪些服务。

### WriteProperty / ReadProperty
- **本质**：BMS 读写 BACnet 对象值的核心服务——ReadProperty 取值，WriteProperty 发命令/设定值。
- **场景**：控制器读传感器值、下发控制逻辑、回写确认。
- **坑/判据**：这是「无自定义集成」的关键——只要对方支持标准 Read/WriteProperty，传感器数据就能被 BMS 直接读写，无需中间件。

### COV（Change of Value，变化通知）
- **本质**：订阅式上报机制——值变化超过阈值才通知，而非固定轮询。
- **场景**：传感器密集、需即时响应但又要省带宽的部署。
- **坑/判据**：COV 订阅比轮询省带宽和算力；需双方支持 SubscribeCOV；设好阈值，否则变化频繁会刷屏。

### BACnet Properties
- **本质**：BACnet 对象的标准属性（状态、行为、上下文）。
- **场景**：描述一个「点」的完整语义。
- **坑/判据**：关键属性：Present_Value（当前值）、Status_Flags（故障/超驰）、Units（单位）、Priority_Array（命令优先级）、Reliability（数据质量）；集成时务必保留单位/状态/可靠性，否则数据到 BMS 后语义丢失。

### PICS（协议实现一致性声明）
- **本质**：厂商出具的正式文档，声明设备支持哪些 BACnet 特性、服务、对象类型、通信能力。
- **场景**：多厂商集成前做兼容性核对、规划集成。
- **坑/判据**：采购前「必查 PICS」——它是设备能否与现有系统互操作的唯一权威依据，别信口头承诺。

### BIBBs（BACnet 互操作构建块）
- **本质**：标准化的服务分组，定义某类设备角色的最低功能要求。
- **场景**：判断不同厂商设备能否互操作的「最小公约数」。
- **坑/判据**：与 PICS 配合使用——PICS 说「支持什么」，BIBB 说「这个角色至少要什么」，两者对齐才保证互操作。

## 四、BACnet 寻址 / 网络

### Device Instance Number（设备实例号）
- **本质**：BACnet 网络上每个设备唯一的数字标识，用于寻址、发现、通信。
- **场景**：Who-Is / I-Am 发现、多厂商多设备环境下的唯一区分。
- **坑/判据**：全网必须唯一，否则发现和寻址冲突；规划时统一分配段，避免现场撞号。

### Network Number（网络号）
- **本质**：每个 BACnet 网段的唯一标识，用于跨网段路由。
- **场景**：跨子网/跨介质的可扩展架构。
- **坑/判据**：路由器依赖网络号决定报文往哪转发；多网段架构必须全局唯一，否则路由错乱。

### Max APDU Length（最大 APDU 长度）
- **本质**：设备能收发的 BACnet APDU 最大尺寸。
- **场景**：受限控制器、混合设备能力的现场。
- **坑/判据**：两端 Max APDU 不匹配会导致大报文通信失败——网关侧做分段（segmentation）适配；集成时对齐该参数是隐性硬坑。

### Priority Array（优先级数组）
- **本质**：命令优先级 1–16，最高有效优先级决定生效值，数字越小优先级越高；低优先级解除后次高接管。
- **场景**：多个控制源（操作员、排程、安全、手动超驰）争抢同一个点的场景。
- **坑/判据**：这是 BACnet 命令仲裁的核心——集成传感器数据时别破坏既有优先级结构，否则会「覆盖安全联锁」。

### BACnet Mapping（BACnet 映射）
- **本质**：把外部数据源（IoT 传感器等）映射到正确的 BACnet 对象、属性、单位、数据类型，使其「原生化」。
- **场景**：把 LoRaWAN 等无线传感数据接入 BMS。
- **坑/判据**：在网关边缘做映射，省去自定义脚本和中间件；映射必须带单位/状态/可靠性，否则 BMS 显示/趋势/逻辑全错。

### Virtual BACnet Devices（虚拟 BACnet 设备）
- **本质**：把非原生数据源（LoRaWAN 传感器、云服务）软件定义成标准 BACnet 设备。
- **场景**：让无线/外部传感点像传统 BACnet 点一样被发现、趋势化、参与逻辑。
- **坑/判据**：好处是简化架构、降集成复杂度；要确保虚拟设备被分配了合法的 device instance / 对象 / 属性，才能被 BMS 正确识别。

## 五、BACnet 网络组件 / 集成

### BACnet Router（路由器）
- **本质**：连接多个 BACnet 网段（如 MS/TP ↔ IP）并在其间路由的设备。
- **场景**：跨介质、跨子网的可扩展楼宇自控架构。
- **坑/判据**：路由器连「同协议不同网络」；网关做「异协议翻译」，两者别混用。

### BACnet Gateway（网关）
- **本质**：在 BACnet 与其他协议（Modbus、LoRaWAN、MQTT）间做协议翻译的设备。
- **场景**：把非 BACnet 设备接入楼宇自控系统。
- **坑/判据**：路由器 = 同协议桥接，网关 = 异协议翻译；选型看「目标系统说哪种协议」，别用路由器去翻译协议。

### BBMD（BACnet 广播管理设备）
- **本质**：让广播消息跨越多个 IP 子网/VLAN（默认广播被路由器阻断）的设备。
- **场景**：BACnet 设备分布在不同 VLAN 或 IP 段的园区网。
- **坑/判据**：跨子网部署时 Who-Is / I-Am 发现会失效，必须每子网配 BBMD 做广播转发；漏配是「发现不到设备」的常见根因。

### JACE / Niagara Framework
- **本质**：Tridium 的楼宇集成平台，聚合管理 BACnet 及多厂商 IP 系统数据，做监控/控制/分析。
- **场景**：系统集成商连接多厂商设备、归一化数据、搭建应用。
- **坑/判据**：Niagara 是行业事实集成中枢，选型时确认网关能「以原生 BACnet 对象」呈现传感器数据，否则要写自定义驱动。

### LoRaWAN-to-BACnet Integration（LoRaWAN 转 BACnet 集成）
- **本质**：把 LoRaWAN 无线传感遥测翻译成标准 BACnet 对象/属性，经 BACnet/IP 上送。
- **场景**：给既有楼宇自控加无线传感，不动既有架构。
- **坑/判据**：边缘网关完成协议翻译，免自定义中间件/系统重构；是「老楼低成本加传感器」的性价比路径，选型看网关是否原生支持该映射。

## 六、底层传输 / 消息协议

### RS-485
- **本质**：差分平衡串行传输的电气标准（TIA/EIA-485），抗噪、远距、多挂载。
- **场景**：工业自动化、过程控制、HVAC、门禁等长距可靠串行通信；是 Modbus RTU / BACnet MS/TP 的物理层。
- **坑/判据**：只是电气层，协议要另选（Modbus、BACnet MS/TP）；两端要加终端电阻防反射，半双工需轮流发言；典型挂载 32 节点。

### TCP/IP
- **本质**：互联网事实标准的四层协议栈（应用/传输/网际/链路），分包传输、可靠重传。
- **场景**：几乎所有联网设备与云端/服务器通信的基础。
- **坑/判据**：可靠但有小开销（打包/分层/握手）；IoT 低功耗场景常用更轻的 UDP/MQTT over TCP 权衡。

### DHCP
- **本质**：自动分配 IP 地址及网关/DNS 等配置，无需手工配 IP。
- **场景**：设备频繁进出网络的环境（企业/家庭/公共 Wi-Fi）与 IoT 批量开通。
- **坑/判据**：租约到期会续租，DHCP 服务器单点故障会导致整段失联；关键/固定点位设备建议静态 IP 或 DHCP 保留。

### MAC（Media Access Control）
- **本质**：数据链路层的子层，负责介质访问控制（CSMA/CD、CSMA/CA 防冲突），MAC 地址是网卡唯一标识。
- **场景**：同一共享介质上的设备寻址与带宽共享。
- **坑/判据**：MAC 地址是二层的「身份证」，做设备识别/白名单/绑定时用；但可被伪造，安全场景不能仅靠 MAC。

### APDU（Application Protocol Data Unit）
- **本质**：BACnet 的标准化报文格式，封装服务请求、响应和对象数据。
- **场景**：BACnet 设备间交换数据/命令/服务的最小单元。
- **坑/判据**：与 Max APDU Length 强绑定——超出对端能力的大报文要分段；网关侧把传感数据封装成合规 APDU 是集成的底层动作。

### Message Broker（消息代理）
- **本质**：用发布-订阅模型解耦设备与应用的通信中间件，按 topic 路由消息。
- **场景**：设备与云端解耦、多对多数据分发、横向扩展、削峰。
- **坑/判据**：MQTT 轻量适合低带宽 IoT，AMQP/Kafka 适合企业/大吞吐；选型看「是否需要持久化 + 吞吐量 + 协议生态」。

### QoS（服务质量）
- **本质**：网络/系统按可靠性、时延、吞吐等指标交付数据包的能力。
- **场景**：保障关键业务流量的优先传输。
- **坑/判据**：MQTT QoS 三档——0（至多一次/丢就丢）、1（至少一次/可能重复）、2（恰好一次/最慢）；要「不丢不重」且关键业务用 QoS 1/2，普通遥测用 0 省开销。

### Smart Meter（智能电表）
- **本质**：实时记录电/气/水用量并通过无线通信回传的先进计量设备，是 AMI 的核心。
- **场景**：用电实时反馈、分时电价、需求响应、故障快速发现。
- **坑/判据**：连接方式（蜂窝/LoRaWAN）决定覆盖与成本；是「海量低频设备」的典型用例，直接对应 LPWAN 选型逻辑。

## 选型速查表

### BACnet 传输方式对比

| 方式 | 物理层 | 安全 | 带宽 | 距离 | 适用场景 |
|---|---|---|---|---|---|
| MS/TP | RS-485 | 无加密 | 低（9.6–76.8 kbps） | 数百米 | 存量串行现场控制器 |
| BACnet/IP | 以太网/Wi-Fi | 弱（需 BBMD 跨子网） | 高 | 园区网 | 企业可扩展部署 |
| BACnet/SC | IP + TLS 1.3 | 强（加密认证） | 高 | 云/公网 | 合规、云连接、跨站点 |

### 协议 / 组件角色对照

| 组件 | 角色 | 关键判据 |
|---|---|---|
| BACnet Router | 同协议跨网段桥接 | 别用于异协议翻译 |
| BACnet Gateway | 异协议翻译 | Modbus/LoRaWAN/MQTT ↔ BACnet |
| BBMD | 跨子网广播转发 | 跨 VLAN 发现设备必配 |
| JACE/Niagara | 集成中枢/归一化 | 确认网关以原生 BACnet 呈现 |
| 虚拟 BACnet 设备 | 非原生源「原生化」 | 需合法 device instance + 对象 |
| Message Broker | 发布-订阅解耦 | MQTT 轻量 / Kafka 大吞吐 |

### 最有用的一条结论

**BACnet 集成的三大隐性硬坑，选型前必须先对齐：① Max APDU Length 两端不一致会导致大报文通信失败；② 跨子网必须配 BBMD，否则 Who-Is/I-Am 发现不到设备；③ 传感器映射必须带 Units / Status_Flags / Reliability，否则数据到 BMS 后语义丢失。** 这三个问题不解决，比协议本身选错更致命。
