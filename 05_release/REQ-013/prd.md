## 需求背景

### 背景说明

EG71 当前已支持 BACnet、Modbus、KNX、LoRaWAN 等多种楼宇协议，但 **M-Bus（Meter-Bus，EN 13757）** 尚未支持。M-Bus 是欧洲楼宇分户计量场景的事实标准，广泛应用于热量表、水表、电表、燃气表等能耗计量仪表的集中抄读。

缺少 M-Bus 支持意味着 EG71 无法进入以下场景：

- 欧洲商业楼宇的能耗分项计量与分户计费
- 替换存量 M-Bus 网关的改造项目
- 需要同时接入计量仪表（M-Bus）和控制设备（Modbus/KNX/BACnet）的混合场景

竞品 **Wattsense** 已支持 M-Bus，补齐该协议是 EG71 楼宇协议覆盖的关键一步。

> ⚠️ 目前存在由于 M-Bus 不支持导致的项目阻塞。涉及客户：HOROS、Communica、SIEMENS、HSYCO。



### 目标与价值

使 EG71 能够作为 M-Bus 主站接入总线上的从站计量仪表并采集数据，覆盖 **新建部署、日常运维、设备变更** 三大核心场景。M-Bus 数据可纳入现有数据流转发和 Node-RED 本地自动化流程，实现"采-传-控"一体化。



### 成功指标

| 指标 | 当前值 | 目标值 | 衡量方式 |
|-|-|-|-|
| M-Bus 设备扫描发现率（标准 EN 13757-3 设备） | - | ≥ 95% | 实测多种仪表 |
| 20 台设备总线扫描完成时间（2400 bps） | - | ≤ 3 分钟 | 用户测试 |
| 手动添加单台设备操作耗时 | - | ≤ 1 分钟 | 用户测试（从进入页面到设备创建成功） |

## 术语表

| 术语/缩写 | 定义（仅限本文档内） |
|-|-|
| M-Bus | Meter-Bus，仪表总线协议（EN 13757），用于能耗计量仪表的集中抄读 |
| 主站（Master） | M-Bus 总线上的主控设备，在本需求中专指 EG71 网关 |
| 从站（Slave） | M-Bus 总线上的计量仪表（热量表、水表、电表等） |
| 一次地址（Primary Address） | M-Bus 从站的 1 字节总线通信地址，范围 1–250，可修改 |
| 二次地址（Secondary Address） | M-Bus 从站的 8 字节出厂唯一标识（厂商ID + 版本 + 介质类型 + 4字节序列号），不可修改 |
| REQ_UD2 | Request User Data 2，主站向从站请求用户数据的标准命令（CI=0x5B） |
| RSP_UD | Respond User Data，从站响应 REQ_UD2 的数据帧，包含固定头 + 数据记录 |
| SND_NKE | Send Normalize，链路层初始化命令，用于重置从站 FCB 状态 |
| SND_UD | Send User Data，主站向从站发送数据的命令（用于地址分配等写操作） |
| DIB | Data Information Block，数据信息块 = DIF + 0\~N个 DIFE，描述数据类型和格式 |
| VIB | Value Information Block，数值信息块 = VIF + 0\~N个 VIFE，描述物理量和倍率 |
| DIF | Data Information Field，1 字节，控制数据类型、功能类型（瞬时/最大/最小/错误） |
| DIFE | DIF Extension，可选扩展字节，控制存储编号、费率、子设备 |
| VIF | Value Information Field，1 字节，控制物理量类别和倍率 |
| VIFE | VIF Extension，可选扩展字节，扩展物理量或修饰符 |
| ACD | Access Demand Class 1，从站有 Class 1 数据待读取 |
| CI | Control Information，控制信息字段，标识帧类型（如 0x52=选中从站, 0x5B=REQ_UD2） |
| BCD | Binary-Coded Decimal，二进制编码十进制，二次地址序列号为 4 字节 BCD |
| 二次地址树搜索 | ~~基于 IEC 60870-5-2 的~~ M-Bus 设备发现算法，逐层匹配二次地址找到所有从站 |
| EN 13757 | 欧洲 M-Bus 标准体系（-2: 物理层, -3: 应用层） |
| 8E1 | M-Bus 串口参数：8 数据位 + 偶校验 + 1 停止位（标准强制要求） |

## 用户与场景

### 用户角色

| 用户角色 | 简要描述 | 使用频率 |
|-|-|-|
| **现场调试工程师（SI）** | 负责楼宇项目现场的网关安装、M-Bus 设备接入和调试，需要快速完成设备接入、减少现场驻留时间 | 项目交付期集中使用 |
| **楼宇运维人员** | 负责楼宇设备日常运营维护，关注设备状态可视化、异常及时发现和定位 | 日常巡检，每周 2–3 次 |
| **BMS 集成工程师** | 负责将 M-Bus 计量数据接入上层 BMS 或本地自动化系统 | 项目集成阶段使用 |



### 核心场景与用户旅程

#### 场景一：新建部署 — 首次接入 M-Bus 仪表

- **触发条件** ：现场调试工程师在楼宇机房完成 EG71 网关安装，M-Bus 总线上的热量表、水表等计量仪表已接线完成
- **用户目的** ：让网关快速发现总线上有哪些仪表、每个仪表能提供哪些计量数据，完成设备注册和数据接入
- **关注信息** ：发现了哪些仪表（厂商、类型、型号）；每台仪表能提供哪些计量数据（能耗 kWh、流量 m³/h、温度 °C、功率 kW）；数据是否合理（扫描时返回的实时数值是否在预期范围内）；设备铭牌序列号与扫描结果二次地址是否匹配
- **用户旅程（步骤）** ：

  1. 网关接入 M-Bus 总线 → 系统自动检测总线电压，接口自动启用，无需手动配置通信参数
  2. 进入【设备数采】→【设备】→「扫描添加」→「扫描 M-Bus」→ 进入分步引导（扫描配置 → 扫描进度弹框 → 选择设备与对象）
  3. 步骤一确认扫描模式（完整扫描/掩码扫描）和自动分配一次地址，点击下一步 → 弹出扫描进度弹框
  4. 网关自动执行二次地址树搜索，实时展示"正在扫描…已发现 X 台设备，Y 个对象"和进度条 → 扫描完成后自动进入步骤二
  5. 步骤二中扫描结果按同型号自动分组（厂商+介质+数据点签名），设备名称自动生成（可编辑），对象列表展示名称/单位/类型/DIB/VIB/值 → 默认全选、确认添加
  6. 确认添加 → 设备和数据对象保存入库，跳转设备列表，开始周期采集
- **关联功能模块** ：5.1 接入网络管理、5.2 设备扫描添加、5.5 数据对象管理、5.6 数据采集



#### 场景二：增量扩展 — 已运行总线上新增设备

- **触发条件** ：楼宇新增了一批水表，已接入 M-Bus 总线，运维人员需要在不停机的情况下将新设备纳入采集范围
- **用户目的** ：不影响已有设备的数据采集，仅添加新设备
- **关注信息** ：哪些是新设备（扫描结果自动过滤已添加设备，顶部汇总行告知总线全貌）；新设备类型和数据项是否与已有设备一致；添加过程是否影响现有数据采集
- **用户旅程（步骤）** ：

  1. 进入【设备】→「扫描添加」→「扫描 M-Bus」
  2. 扫描过程中已有设备保持正常采集，不受影响 → 进度弹框实时展示
  3. 步骤二展示汇总信息（"总线共发现 X 台设备，其中 Y 台已添加、Z 台为新设备"），下方仅展示新发现设备
  4. 勾选新设备及对象后确认添加
- **关联功能模块** ：5.2 设备扫描添加、5.4 设备管理



#### 场景三：少量设备接入或单台设备替换

- **触发条件** ：工程师已知目标设备地址（如从设备铭牌或项目文档获取），只需添加 1–2 台设备；或在设备替换场景中先添加新设备再复制对象配置
- **用户目的** ：快速完成单台或少量设备的接入，避免全总线扫描的等待时间
- **关注信息** ：设备能否正常通信（填入地址后是否能成功读取设备信息）；替换场景中新设备的数据对象是否与旧设备一致（复制对象配置后数据采集能否无缝衔接）
- **用户旅程（步骤）** ：

  1. 进入【设备】→「手动添加」→ 选择协议类型「M-Bus」
  2. 步骤一填写设备名称、选择寻址方式（一次地址/二次地址）、填入地址、可选填写描述 → 点击下一步
  3. 设备立即创建（状态「从未上线」），网关后台异步验证设备可达性并自动更新状态（后端更新设备状态的1分钟之后才会同步到前端界面）
  4. 步骤二可选择扫描添加对象 / 手动添加对象 / 跳过直接返回设备列表
  5. （替换场景）从旧设备复制对象配置到新设备 → 确认新设备采集正常 → 删除旧设备
- **关联功能模块** ：5.3 设备手动添加、5.4 设备管理、5.5 数据对象管理



#### 场景四：预配置 — 设备/总线尚未就绪时提前配置

- **触发条件** ：工程师在办公室或施工现场布线前，已拿到项目规划文档，知道将要接入的仪表地址清单，希望提前在网关中完成设备配置
- **用户目的** ：提前完成设备配置，现场总线上电后网关自动开始采集，无需现场等待
- **关注信息** ：预配置的设备在总线上电后能否自动上线（后台异步探测，设备可达后自动更新状态为「在线」）；预配置期间是否影响其他操作（状态为「从未上线」，不影响正常设备采集）
- **用户旅程（步骤）** ：

  1. 手动添加设备，填写已知的地址信息
  2. 设备创建后状态为「从未上线」，不阻塞操作
  3. 后续网关接入总线、设备上电后，后台异步探测自动更新状态为「在线」
- **关联功能模块** ：5.3 设备手动添加、5.4 设备管理



#### 场景五：网关替换 — 替换总线上已有的 M-Bus 主站（预留，待调研）

- **触发条件** ：楼宇已有一套 M-Bus 采集系统在运行，需要替换为 EG71
- **用户目的** ：用 EG71 接管现有总线，尽可能减少对计量数据采集的中断
- **关注信息** ：切换过程中数据采集会中断多久；已有设备的地址和配置能否迁移到新网关；新网关采集的数据是否与旧系统一致
- **用户旅程（步骤）** ：待调研 — 此场景的技术方案依赖 EG71 M-Bus 硬件能力（如是否支持纯监听模式以嗅探总线通信）和客户实际需求调研，MVP 阶段暂不交付完整方案
- **关联功能模块** ：N/A（待调研）

### 接入网络管理

#### 功能定位

- **边界** ：提供 M-Bus 接入网络的预置、~~自动启用/禁用、~~查看和编辑能力。M-Bus 接入网络由网关出厂预置（一个网关仅一个），用户无需手动创建，不可删除。
- **解决的痛点** ：降低客户认知负担——M-Bus 作为网关内置接口应"开箱即用"，客户直觉是"接上线就能用"。



#### 设计决策



| 决策点 | 方案选择 | 理由 |
|-|-|-|
| 网络预置 vs 用户创建 | **网关预置**，用户无需创建 | 降低认知负担；EG71 硬件仅 1 路 M-Bus，无多网络场景 |
| 启用逻辑 | M-Bus 接口检测到总线接入 → **自动启用**；总线断开 → 自动变更为未启用 | 契合客户"接上线就能用"的直觉，启用/禁用由硬件状态驱动 |
| 校验位和停止位 | 固定 8E1（校验位默认Even，停止位默认1），**不对用户展示** | EN 13757-3 标准强制要求，用户无需关心也无法更改，如存在不一致不符合8E1的，设备端可调整 |
| 通信时序参数 | 帧间延时（50ms）/ 响应超时（2000ms）/ 重试次数（1）作为 **高级配置**，默认折叠 | 对齐竞品 Wattsense 的高级调参能力，同时保持主流用户的简洁体验 |
| 不可删除 | **不允许删除** | 网关预置通道，删除无意义且可能导致配置丢失 |
| 波特率修改影响 | 修改后 **自动执行 SND_NKE** 重置链路层 | 波特率变更导致主从两端 FCB 状态不可靠，须重新同步 |



#### 功能概述

- **一句话描述** ：M-Bus 接入网络由网关预置，用户无需创建；用户可按需编辑名称、波特率和高级通信参数。
- **典型操作路径** ： `现场调试工程师 → 【设备采集】→【设备接入网络】→ 查看/编辑 M-Bus → 修改名称/波特率（展开高级配置可选）→ 保存`

### 设备扫描添加

#### 功能定位

- **边界** ：解决现场调试工程师在 M-Bus 总线上批量发现和接入设备的问题。工程师无需事先知道总线上有哪些设备、每台设备的地址是什么，网关通过标准 M-Bus 二次地址树搜索自动发现所有从站设备及其数据对象。仅展示新发现设备，已添加设备基于二次地址过滤。
- **解决的痛点** ：现场施工中总线上挂了多少台仪表、每台仪表的通信地址通常不清楚（总线由施工方统一布线，仪表来自不同批次/厂商），手动逐台输入低效且易错。



#### 设计决策

| 决策点 | 方案选择 | 理由 |
|-|-|-|
| 扫描方式 | **仅二次地址树搜索** | 一次地址全量扫描需遍历 1–250，实际设备少的情况下（几个或几十个表时）耗时长且；大部分客户主要用二次地址管理；树搜索基于唯一标识，遍历次数少；大部分设备出厂的一次地址为空或1，会出现冲突情况 |
| 设备+对象同时扫描 | **REQ_UD2 一次性返回身份+数据** | M-Bus 协议特性 — RSP_UD 固定头含设备身份，用户数据区含全部对象 DIB/VIB |
| 交互模式 | **分步引导** （扫描配置 → 进度弹框 → 选择设备与对象） | 降低每步认知负担，对齐 BACnet 扫描成熟交互模式 |
| 自动分组维度 | 厂商代码 + 介质类型 + **数据点签名** | 同型号设备共享相同的对象列表，分组后可批量管理，效率更高 |
| 地址冲突处理 | 扫描阶段 **检测+展示** （折叠+xlsx下载），一次地址冲突设备可添加仅告警，二次地址冲突设备不可添加 | 冲突根源需现场物理排查（断开总线逐设备通电定位），网关无法远程修复 |
| 增量扫描 | 基于 **二次地址** 过滤已添加设备 | 二次地址是设备唯一标识，比一次地址更可靠 |
| 扫描模式 | 完整扫描（全网树搜索）/ 掩码扫描 （8位BCD mask限定搜索范围） | 大型总线或已知序列号范围时，掩码扫描可大幅缩短扫描时间；掩码扫描第一位固定为通配（F），确保掩码扫描始终是范围搜索，如果 8 位全部可配置为具体数字，等价于精确指定单台设备，直接用手动添加即可，无需使用掩码扫描。 |
| 数据记录区分 | 记录位置 | 当同一设备存在 DIB+VIB 相同的多个对象时，通过记录位置区分。可参照设备手册中的数据记录顺序填写。 |



#### 功能概述

- **一句话描述** ：通过分步引导（扫描配置 → 进度弹框 → 选择设备与对象），自动发现 M-Bus 总线上的从站设备及其数据对象，按同型号分组供用户批量勾选确认。
- **典型操作路径** ： `现场调试工程师 → 【设备数采】→【设备】→「扫描添加」→「扫描 M-Bus」→ 步骤一：确认扫描模式+自动分配一次地址 → 点击下一步 → 扫描进度弹框（可中途停止）→ 步骤二：勾选设备和对象 → 确认添加 → 跳转设备列表`

##### 扫描机制说明

###### 二次地址树搜索

M-Bus 设备扫描基于 **二次地址树搜索算法** （EN 13757-2 / IEC 60870-5-2）。每台 M-Bus 从站有一个 8 字节全球唯一的二次地址，包含序列号（4 字节 BCD，即 UI 中 8 位 BCD mask 对应的部分）、厂商代码（2 字节）、版本（1 字节）、设备类型（1 字节）。

树搜索通过向总线反复发送 **Selection of Slaves（CI=0x52）** 命令——命令中携带带有通配符 `F` 的二次地址模式（ `F` 代表该位匹配任意数字）——逐步缩小匹配范围，直到精确锁定每一台从站。

响应判断规则：

| 响应结果 | 含义 | 后续动作 |
|-|-|-|
| 收到 E5（单字节 ACK） | 当前模式唯一匹配一台设备，锁定成功 | 对该设备执行 REQ_UD2 读取数据 |
| 无响应 | 当前前缀下无设备 | 剪枝，跳过该分支 |
| 收到乱码 / 校验失败 | 多台设备同时响应、电流叠加冲突 | 细化：将当前最高通配位依次替换为 0–9，生成 10 个子分支递归搜索 |

示例：总线上 3 台表序列号为 1234、5678、1299（以 4 位 BCD 简化）：

| 步骤 | 发出通配模式 | 响应 | 动作 |
|-|-|-|-|
| 1 | FFFF | 3 台同时响应 → 冲突 | 细化第 1 位 |
| 2 | 1FFF | 1234 + 1299 → 冲突 | 细化第 2 位 |
| 3 | 12FF | 1234 + 1299 → 冲突 | 细化第 3 位 |
| 4 | 123F | 仅 1234 → E5 ✅ | 锁定，执行 REQ_UD2 |
| 5 | 129F | 仅 1299 → E5 ✅ | 锁定，执行 REQ_UD2 |
| 6 | 5FFF | 仅 5678 → E5 ✅ | 锁定，执行 REQ_UD2 |

实际 8 位 BCD 搜索时，20 台设备的总线通常几十次迭代内完成，约 30 秒–3 分钟（2400 bps）。

###### 完整扫描（Full Scan）执行逻辑

用户选择「完整扫描」时，网关以 **全通配** （序列号 8 位全为 `F` 、其余字段全通配）为初始条件发起树搜索，遍历总线上所有可响应设备。

**执行步骤：**

1. 以全通配二次地址发出 Selection 命令
2. 根据响应结果决定下一步：
3. 无响应 → 该分支剪枝结束；
4. 收到 E5 → 唯一锁定，进入单台设备完整处理流程（见第5.2.4.2.5节）；
5. 收到冲突 → 对当前最高通配位逐一替换为 0–9，形成 10 个子分支，每个子分支重复本步骤
6. 所有分支遍历完成后，扫描结束，自动跳转步骤二

**边界规则：**

- 覆盖整个 8 位 BCD 序列号空间，不遗漏任何可响应设备
- 已在本次扫描中完整处理的设备不重复处理

###### 掩码扫描（Mask Scan）执行逻辑

用户选择「掩码扫描」并填写 8 位 BCD mask 后，网关仅在用户指定的序列号范围内执行树搜索，跳过不符合 mask 的所有分支。

**mask 规则：**`F` = 该位通配（允许大小写，输入小写时自动转成大写），搜索时可细化为 0–9； `0–9` = 该位固定，搜索时保持该数字不变，不展开子分支。

**执行步骤：**

1. 网关先校验 mask：8 位全为 F 时前端拦截，提示用户改用完整扫描
2. 以用户填写的 mask 作为初始 Selection 命令发出
3. 根据响应结果决定下一步：
4. 无响应 → 该分支剪枝结束；
5. 收到 E5 → 唯一锁定，进入单台设备完整处理流程；
6. 收到冲突 → 仅对当前值为 F 的位细化（固定数字位始终保持不变），形成子分支，重复本步骤
7. 所有满足 mask 的分支遍历完成后，扫描结束，自动跳转步骤二

**示例：** mask 填 `F4900FFF` ，网关只搜索序列号满足 `?4900???` 模式的设备（第 1 位 F 始终通配，第 2–5 位固定为 4900，第 6–8 位 FFF 可细化）。

**边界规则：**

- 固定数字位在整个搜索过程中不参与分叉
- 扫描范围和速度随 mask 中固定数字位的数量成比例缩减

###### 扫描进度百分比计算逻辑

扫描进度弹框中展示当前扫描进度百分比，帮助用户了解扫描推进情况。

**进度计算逻辑**

进度百分比 = 已探索的地址空间 / 总地址空间 × 100%

| **扫描模式** | **总地址空间（分母）** | **计算方式** |
|-|-|-|
| 完整扫描 | 10^8 = 100,000,000 | 8 位 BCD 全部遍历 |
| 掩码扫描 | 10^N（N = mask 中 F 的位数） | 仅遍历 mask 中 F 对应的位 |

掩码扫描示例：mask = `F 4 9 0 0 F F F`，4 个 F 位 → 总地址空间 = 10^4 = 10,000。

**已探索地址空间（分子）**

树搜索过程中，每完成一个分支的搜索后，计入该分支对应的叶子地址数

- 分支搜索到设备（该分支下钻完毕）→ 计入该分支对应的叶子地址数
- 分支无设备响应（空剪枝）→ 一次性跳过，计入该分支对应的叶子地址数

**更新逻辑**

- 更新时机：树搜索每完成一个分支的搜索时触发一次进度刷新
- 表现特征：设备密集的号段进度增长较慢（持续下钻），设备稀疏的号段进度增长较快（快速剪枝），总体趋势从左到右递增至 100%

**弹框展示内容**

| **展示项** | **说明** |
|-|-|
| 进度百分比 | 已探索地址 / 总地址空间 × 100%，保留整数，四舍五入展示最终百分比 |
| 已发现设备数 | 当前已发现的设备台数 |
| 已发现对象数 | 当前已发现的数据对象总数 |

###### 单台设备完整处理流程（流水线式）

两种扫描模式均采用 **流水线式** 执行：唯一锁定一台设备后，立即完成该设备的全部步骤，再继续搜索下一个分支。

```
[Step A] 唯一锁定
         通过二次地址树搜索定位单台设备（Selection 命令收到 E5 应答）
       ↓
[Step B] 发 REQ_UD2（A=0xFD，仅该设备响应）
         读取固定头：厂商、版本、设备类型、二次地址
         解析全部 DIB/VIB 数据对象列表，记录每条数据在帧中的顺序号，用于DIB+VIB重复场景的数据区分
         ↓ 超时/失败 → 丢弃，搜索下一分支
       ↓
[Step C] 检查一次地址
         ├─ 固定头含 VIF=0x7A 且值 > 0 → 记录已有一次地址
         ├─ 固定头含 VIF=0x7A 但值为 0 → 视为无有效一次地址
         └─ 无 VIF=0x7A → 视为无有效一次地址
       ↓
[Step D] 将设备记入扫描结果集
         - 已有一次地址的设备 → 记录地址值
         - 无一次地址的设备 → 标记"待分配"
         - 同时记录：地址冲突检测结果（一次地址冲突 / 二次地址冲突）
         - 进度弹框更新：
           · 进度百分比 = 已探索地址空间 / 总地址空间 × 100%
           · 已发现设备数 +1
           · 已发现对象数累加
       ↓
[Step E] 继续搜索树的下一分支，直到全部地址空间搜索完毕或用户手动停止
```

**进度计数时机：** 设备计数 和 对象计数更新 发生在扫描进度百分比更新的时候，即进度百分比更新时同时更新设备数量和对象数量。进度弹框中显示的设备数始终是「完整可用设备数」，进度弹框中显示的对象数始终是「完整可用设备数对应已解析的对象数量」，步骤二展示数量与之严格一致。

###### 停止扫描的处理规则

用户点击「停止扫描，下一步」时， **立即停止** ，当前正在执行的设备流程（Step A–D）中止，该设备 **不进入** 结果集。

| 停止时所在阶段 | 处理方式 | 进入步骤二？ |
|-|-|-|
| Step A：等待 Selection E5 中 | 丢弃，不进入结果集 | ❌ |
| Step B：等待 RSP_UD 中 | 丢弃，不进入结果集 | ❌ |
| Step C：RSP_UD 已收到，正在判断一次地址 | 丢弃，不进入结果集 | ❌ |
| Step D：等待 SND_UD 的 E5 中 | 丢弃，不进入结果集 | ❌ |
| Step E 已完成，正在展开新分支 | 立即停止展开新节点 | ✅ 已在结果集中 |

**结果保证：** 步骤二展示的设备数与进度弹框中最后显示的「已发现 X 台设备，Y 个对象」严格一致，不会出现多设备或少设备的情况。

##### 地址冲突检测说明

扫描过程中，系统同时判断 **一次地址冲突** 和 **二次地址冲突** ，并在步骤二以不同方式反馈给用户。两类冲突的业务含义不同，处理方式也不同。

###### **一次地址冲突的判断与反馈**

- 本次扫描结果中，两台及以上设备的一次地址相同
- 本次扫描中新发现的设备，其一次地址与网关中已添加设备的一次地址相同

###### **二次地址冲突的判断与反馈**

**什么情况判定为二次地址冲突：**

##### 设备与对象说明

###### 设备分组聚合逻辑

扫描发现的新设备按以下三个维度完全一致时归为一组：

- **厂商代码** ：从设备固定头中解析的厂商标识（~~根据标识映射厂商名称~~ [厂商映射关系](https://milesight.feishu.cn/docx/Ysx2d9mPGon2QsxeC7wcn8PHnvh#doxcnB1AlRvQ2t19oEU3Ls4HErd) ）
- **介质类型** ：从设备固定头中解析的设备类型（热量表、水表、电表等）
- **数据点签名** ：该设备返回的全部数据对象结构，相同则代表对象列表完全一致

同组设备共享相同的数据对象列表，用户对右侧对象的勾选操作对组内所有已选中设备生效。

**分组标题命名规则：**

- 同一厂商+介质只有一组 → `厂商代码`~~`名称`~~` 介质类型 — X台 × Y个对象`
- 同一厂商+介质有多组（数据点签名不同，即对象结构不一致）→ `厂商代码`~~`名称`~~` 介质类型 Group N — X台 × Y个对象` ，N 按扫描发现顺序从 1 递增

###### 确认添加逻辑

用户在步骤二点击「完成」后，网关依次执行数量校验和两环节添加流程。

- 允许只选设备、不选任何对象 → 设备添加成功，对象数量为 0
- 扫描阶段已成功通信的设备，添加后初始状态为「在线」
- 没有勾选任何设备时（不管是否有勾选对象），无法点击「完成」按钮实现设备&对象添加，即「完成」置灰

**前置校验：数量检查**

网关限制最大M-Bus设备数量为 250 个、所有设备数量为 2,000 个，对象数量为 20,000 个。点击「确认添加」后，需校验对应设备数量或对象数量是否超过上限。

| 校验项 | 限制 | 计算方式 |
|-|-|-|
| 设备数量 | ≤ 250 台 | 当前已有 M-Bus 设备数 + 本次待添加设备数 |
| 网关所有设备数量 | ≤ 2,000 台 | 当前网关所有协议的设备总数（不关心设备状态） + 本次待添加 M-Bus 设备数 |
| 对象数量 | ≤ 20,000 个 | 当前已有对象数（不关心对象启用状态） + 本次待添加对象数 |

两项同时校验，根据结果分三种情况：

**情况一：全部通过** → 进入添加进度弹框

**情况二：仅网关整体设备数量超出 → 弹出提示**

**后台执行逻辑**

**环节一：一次地址分配**

判断本次勾选设备中是否存在"待分配"设备：

- **无待分配设备**：跳过此环节
- **有待分配设备**：逐台处理，执行 SND_UD 写入一次地址

  1. 取候选一次地址（规则见 5.2.4.4.6 章节）
  2. 发 REQ_UD2 探测该地址：
  
     - 无响应 → 地址空闲 → 通过二次地址选中设备（CI=0x52）→ 发 SND_UD 写入一次地址
     
       - 收到 E5 → 写入成功，记录一次地址
       - 超时/失败 → 标记"一次地址分配失败"
     - 有响应 → 地址被占用，取下一候空闲地址探测（~~如果所有地址都被占用 → 标记"一次地址分配失败"~~）

**环节二：设备入库**

逐台处理全部勾选设备（含一次地址分配失败的设备）：

- 已有一次地址 → 直接入库（设备信息 + 对象信息）
- 一次地址分配失败 → 仍入库（以二次地址管理）

###### 自动分配一次地址规则

**执行阶段：**

一次地址分配在确认添加阶段执行，不在扫描阶段执行。扫描阶段仅识别设备是否已有一次地址并标记"待分配"状态，确认添加后才对"待分配"设备执行 SND_UD 写入。

**执行前提判断：**

| 条件 | 是否执行 |
|-|-|
| 用户未勾选「自动分配一次地址」 | ❌ 跳过，设备标记"未分配"，入库后以二次地址管理 |
| 用户勾选，且设备已有一次地址 | ❌ 跳过，使用已有地址直接入库 |
| 用户勾选，且设备无一次地址（标记"待分配"） | ✅ 执行 SND_UD 写入 |

**执行规则：**

- 超时阈值和重试次数取当前接入网络配置中的「响应超时」和「重试次数」
- **候选地址选取策略**：网关采用以下方式选取候选地址，降低与总线上不可见设备冲突的概率

  - **排除已知占用**：从 1–250 中排除已在网关中添加的设备地址和本次扫描会话中已识别设备的地址，从低到高依次选择
  - **按需探测**：在实际写入一次地址前，先向候选地址发送探测请求（REQ_UD2）——无响应则确认地址空闲，可以分配；有响应则说明地址已被总线上其他设备占用，跳过并选择下一个候选地址

**结果处理：**

| 结果 | 一次地址字段 |
|-|-|
| 收到 E5（写入成功） | 存储分配的地址值 |
| 超时/失败（设备不支持 SND_UD） | 标记分配失败，设备仍入库 |

---

##### **业务限制规则**

- 设备数 ≤ 250 台（M-Bus 地址空间上限）
- 扫描结果仅展示新发现的设备，已添加设备基于二次地址过滤
- 对象名称设备内唯一（重复时自动追加功能类型后缀或序号）
- 二次地址冲突设备 **不可勾选添加** ；一次地址冲突设备 **可勾选添加** （仅告警）
- 同一时间仅允许一个扫描任务，进行中时拒绝新扫描
- 冲突信息仅当前扫描会话有效
- 切换左侧设备分组时，右侧已勾选对象状态不被重置

### 设备手动添加

#### 功能定位

- **边界** ：解决工程师在已知设备地址场景下快速添加单台或少量设备的问题，以及设备/总线尚未就绪时的预配置需求。设备创建与状态验证解耦——设备立即创建，后台异步验证设备状态。
- **解决的痛点** ：只有一两台设备时手动输入地址比全总线扫描更快；预配置场景中总线尚未接通时扫描不可用，手动添加是唯一方案。



#### 设计决策

| 决策点 | 方案选择 | 理由 |
|-|-|-|
| 设备创建与验证解耦 | **立即创建 + 后台异步验证** | 支持预配置场景（网关未接总线时也能添加），不阻塞用户流程 |
| 寻址方式 | **一次地址/二次地址二选一** ，默认一次地址 | 给予用户灵活性：已知编号用一次地址，已知序列号用二次地址 |
| 接入网络 | M-Bus 协议下 **不展示接入网络字段** | 网关自动关联预置的 M-Bus 接入网络，减少用户操作 |
| 设备型号 | M-Bus 协议下可选「None」及 M-Bus 协议类型的设备模板 | M-Bus 协议下设备型号默认为「None」；当设备库中已有 M-Bus 协议类型的设备模板时，用户可选择引用模板快速初始化对象配置，提升批量部署效率 |
| 步骤二可跳过 | **对象添加为可选步骤** | 用户可能只想先创建设备，对象后续再配 |



#### 功能概述

- **一句话描述** ：手动添加采用分步引导（两步），步骤一填写设备信息后设备立即创建，步骤二提供可选的对象添加入口。
- **典型操作路径** ： `工程师 → 【设备】→「手动添加」→ 选择「M-Bus」→ 填写名称+寻址方式+地址 → 下一步 → 设备立即创建（状态「从未上线」）→ 步骤二可选扫描/手动添加对象或跳过`

##### 设备状态说明

设备创建后，设备的初始状态为「从未上线」，网关在后台自动向填入的地址发起通信验证，并更新设备状态，整个过程用户无需等待，不阻塞步骤二的操作。

**一次地址寻址的验证**

网关向用户填写的一次地址发送 REQ_UD2。

- 若收到有效 RSP_UD 则验证成功，不解析DIB+VIB内容，仅从固定头提取二次地址存储，并将设备从「从未上线」更新为「在线」
- 若超时则验证失败，设备状态仍然保持「从未上线」
- 若收到多台设备同时应答的混乱信号，说明该一次地址在总线上被多台设备占用（地址冲突），在设备列表中标记 ⚠ 告警，设备状态仍然保持「从未上线」

**二次地址寻址的验证方式**

网关通过 CI=0x52 选中用户填写的二次地址对应的设备，再发 REQ_UD2。

- 若收到有效 RSP_UD 则验证成功，不解析DIB+VIB内容，仅从固定头提取一次地址（VIF=0x7A）存储，无一次地址则标识未分配，并将设备从「从未上线」更新为「在线」
- 若超时则验证失败，设备状态仍然保持「从未上线」
- 若收到多台设备同时应答的混乱信号，说明该二次地址在总线上被多台设备占用（地址冲突），在设备列表中标记 ⚠ 告警，设备状态仍然保持「从未上线」

### 设备管理

#### 功能定位

- **边界** ：提供 M-Bus 设备的列表查看、编辑（右侧抽屉）、删除（级联清理）及设备替换场景的操作能力。设备在线状态通过一次地址优先、二次地址兜底的策略判断，并具备离线降级探测机制。
- **解决的痛点** ：运维人员需要查看和管理 M-Bus 设备信息与状态；调试工程师在设备地址变更时需快速同步。



#### 设计决策

| 决策点 | 方案选择 | 理由 |
|-|-|-|
| 在线状态判断 | **一次地址优先 + 二次地址兜底** | 一次地址通信快（2帧/次），二次地址需先选中（4帧/次）；优先快路径 |
| 离线判定降级 | 一次地址连续超时后 **降级尝试二次地址** ；二次地址也超时才标记离线 | 防止一次地址被现场更改导致误判离线 |
| 一次地址管理 | **用户可在编辑抽屉中直接修改** ；保存时校验不与已有设备冲突 | 一次地址是总线通信地址，现场可变更 |



#### 功能概述

- **一句话描述** ：M-Bus 设备纳入 EG71 现有设备列表，支持查看/编辑/删除。
- **典型操作路径** ： `运维人员 → 【设备数采】→【设备】→ 查看设备列表 → 点击「编辑」→ 右侧抽屉修改名称/一次地址/设备型号/描述 → 保存`

##### 设备状态变更逻辑

设备有三种可能的状态，由网关根据通信结果自动判定。

- **从未上线** ：设备创建后尚未成功通信过
- **在线** ：最近一次通信成功
- **离线** ：设备曾经在线，但通信失败（包括采集连续失败或地址验证失败）



**状态转换规则**

| 触发场景 | 成功 | 失败 |
|-|-|-|
| 手动添加设备 | 从未上线 → 在线 | 保持从未上线 |
| 编辑设备地址 | 任意状态 → 在线 | 从未上线 → 从未上线（保持）  <br/>离线 → 离线（保持）  <br/>在线 → 离线（立即更新） |
| 周期性采集 | 任意状态 → 在线 | 从未上线 → 从未上线（保持）  <br/>离线 → 离线（保持）  <br/>在线 → 离线（连续3次失败） |

**场景一：手动添加设备**

```Plain Text
设备创建（状态：从未上线）
  ↓
后台异步验证
  ├─ 验证成功 → 状态：在线
  └─ 验证失败 → 状态：从未上线（保持）
```

**场景二：编辑设备地址**

```Plain Text
用户修改地址（状态：从未上线 / 在线 / 离线）
  ↓
立即验证新地址
  ├─ 验证成功（一次地址 或 二次地址成功）
  │   ├─ 原状态为「从未上线」→ 在线
  │   ├─ 原状态为「在线」→ 在线（保持）
  │   └─ 原状态为「离线」→ 在线
  └─ 验证失败（一次地址 和 二次地址 均失败） → 保持原状态
```

**场景三：周期性数据采集**

```Plain Text
采集周期到达
  ↓
发送 REQ_UD2 请求
  ├─ 通信成功 → 状态更新为「在线」，失败计数清零
  └─ 通信失败 → 重试（基于 M-Bus 接入网络的配置）
      ├─ 重试成功 → 状态更新为「在线」，失败计数清零
      └─ 重试失败 → 本周期采集失败，失败计数+1
          ├─ 失败计数 < 3 → 保持当前状态
          └─ 失败计数 = 3 → 状态更新为「离线」
```



**探测机制**

- 探测方式：通过 REQ_UD2 命令进行通信验证
- 探测周期：① 手动添加 - 立即触发，② 地址编辑 - 立即触发，③ 周期采集 - 与采集间隔一致
- 探测范围：所有 M-Bus 设备，不区分当前状态

### 数据对象管理

#### 功能定位

- **边界** ：为 M-Bus 设备定义"需要采集哪些数据"。以 DIB（DIF+DIFE）和 VIB（VIF+VIFE）为核心标识，支持扫描添加、手动添加、编辑、启用/禁用、删除、即时读取值。标准 VIF 自动解析物理含义，非标 VIF 需手动配置。
- **解决的痛点** ：M-Bus 仪表一次 RSP_UD 可能返回几十条数据记录，工程师需要选择实际需要的数据项，并对非标对象做语义化标注。



#### 设计决策

| 决策点 | 方案选择 | 理由 |
|-|-|-|
| 对象标识方式 | **DIB + VIB + 记录位置 组合** | 规避DIB+VIB重复的情况，唯一确定一个数据记录 |
| 对象名称 | VIF/VIFE 编码表自动解析， **允许用户手动覆盖** | 部分 VIF 编码对应通用名称，用户可按业务场景自定义 |
| 倍率 vs 线性函数 | **两层独立** ：倍率（协议层自动解析）+ 线性函数 y=ax+b（用户可选配置） | 倍率由VIF编码决定用户不感知；线性函数用于传感器校准或工程值换算 |
| 启用/禁用逻辑 | **复用 EG71 现有机制** | 保持体验一致性，降低开发成本 |
| 对象复制 | 覆盖/新增两种模式 | 覆盖用于替换场景，新增用于增量场景 |



#### 功能概述

- **一句话描述** ：通过扫描添加或手动添加两种方式定义 M-Bus 数据对象，支持编辑、启用/禁用、删除、即时读取值等完整对象生命周期管理。
- **典型操作路径** ： `工程师 → 设备对象管理页 →「+ 扫描添加」（在线设备）→ 进度弹框 → 抽屉展示对象列表 → 勾选 → 确认添加`

##### 启用和禁用对象

- **启用**

  - 对象纳入周期性采集计划，采集数据正常参与转发
- **禁用**

  - 对象从采集计划中移除，不对该对象进行数据解析，不产生新数据
  - 禁用后，该对象的"最新数值""数值更新时间""更新次数"停止更新，保留禁用前的最后值
  - 已配置的转发引用保留，但禁用期间无新数据上报
  - 重新启用后，下一轮采集周期恢复数据解析和数据更新
- **批量操作**

  - 支持勾选多个对象批量启用或批量禁用

##### 复制对象

将已配置设备的对象配置批量复制到其他同型号 M-Bus 设备，用于同型号设备快速部署或设备替换场景。

**前置条件**

| 条件 | 不满足时 |
|-|-|
| 当前设备下至少有一个已配置对象 | 「复制对象」按钮置灰不可点击 |
| 网关内存在相同设备型号的其他 M-Bus 设备 | toast提示「无相同设备型号的其他设备」，不进入操作 |

**业务流程**

1. 用户在对象列表中勾选要复制的对象，点击「复制对象」
2. 选择复制类型：「覆盖」/「新增」，单选，默认「新增」
3. 右侧抽屉展示目标设备列表（排除源设备本身）：

   - 列表字段：设备复选框、设备名称、当前已添加对象数量
   - 设备名称支持模糊搜索，大小写不敏感
   - 支持全选/取消全选
   - 默认不勾选任何设备，由用户自己选择
4. 用户选择目标设备后，点击「保存」
5. 根据复制类型进入对应的校验流程（见下方）
6. 校验通过后执行复制，提示「复制设备对象成功」

##### 即时读取对象值

- **触发条件**

  - 设备当前状态为 **在线** 且 对象当前状态为 **启用** 时，"获取值"按钮可用

  3. 通信失败时，toast提示"获取值失败"
- **与周期性采集的关系**

  - 即时读取不影响下一次周期性采集的时间点

### 数据采集

#### 功能定位

- **边界**：数据采集引擎以设备为维度，周期性地对 M-Bus 设备发起抄读并解析存储数据到本地。采集范围包含 Class 2 计量数据，以及通过 ACD 检测按需采集的 Class 1 告警数据。该模块是连接「配置」与「数据消费（数据流/数据转发/Node-RED）」的核心桥梁。
- **解决的痛点** ：用户配好设备和对象后核心诉求是"配好就能用"——网关自动按周期读取仪表数据并存储，无需人工干预。



#### 设计决策

| 决策点 | 方案选择 | 理由 |
|-|-|-|
| 最小调度单元 | 以设备为维度 | M-Bus 协议一次通信返回设备全部数据记录 |
| 采集间隔粒度 | 设备级统一间隔 | 采集间隔配置在设备级别，该设备下所有已启用对象按同一频率采集 |
| 采集范围 | 仅采集在线设备 | 离线/从未上线设备不纳入调度，避免无效通信阻塞总线 |
| 并发策略 | 顺序轮询，非并发 | M-Bus 为半双工总线，同一时刻只能一台设备通信 |
| 数据存储 | 采集成功后存储到本地 | 数据转发模块从本地存储获取数据进行转发，采集引擎不直接参与数据转发 |
| Class 1 采集触发依据 | 依据 ACD 标志位 | ACD=1 即表示表计有 Class 1 数据待读取，网关应直接响应；不支持 Class 1 的表计 ACD 不会为 1 |
| Class 1 采集时机 | REQ_UD2 响应完成后立即发送 REQ_UD1 | 告警信息对用户优先级较高，紧随 REQ_UD2 采集可最快获取告警；不切换通信对象，总线效率影响最小 |



#### 功能概述

- **一句话描述**：采集引擎按各设备配置的采集间隔，周期性对 M-Bus 设备发起 REQ_UD2 抄读 Class 2 计量数据，按 DIB+VIB+记录位置匹配已启用对象后存储到本地；同时检测每台设备响应帧中的 ACD 标志位，对有待读告警的设备紧随 REQ_UD2 发起 REQ_UD1 采集 Class 1 告警数据，解析后供数据转发使用。



#### 功能逻辑

##### **采集调度规则**

- **调度范围**

  - 所有已添加的 M-Bus 设备
  - 非在线状态的设备也需要通过触发采集通信来更新设备状态
- **调度策略**

  - 每台设备独立按照自己配置的采集间隔进行调度
  - ~~当多台设备的采集间隔同时到期时，按设备添加顺序排队执行~~
- **任务过期机制**

  - 每个采集任务有有效期，有效期 = 采集间隔
  - 任务到期后如果在队列中等待超过有效期，则自动丢弃
  - 丢弃后等待下个采集周期重新生成任务
  - 采用竞争机制（跟现有逻辑一致），极端情况下牺牲部分数据采集，避免雪崩
- **业务效果**

  - 当设备数量较多、总线负载较高时，部分采集任务可能被丢弃
  - 被丢弃的任务会在下个周期重新调度
  - 系统始终保持响应能力，不会出现任务堆积导致系统瘫痪
  - 无对象的设备也会按周期通信，确保状态及时更新

> 典型楼宇项目中，一般一栋楼10\~50个M-Bus设备，普通商业楼宇项目每小时采集一次即可。按现有调度逻辑不会导致总线负载过高影响数据采集的结果。

##### **单设备采集流程**

**业务流程：**

```Plain Text
采集开始
    │
    ├── 寻址并请求数据（REQ_UD2）
    │
    ├── 等待设备响应（根据接入网络配置重试）
    │   │
    │   ├── 响应成功 → 继续
    │   │   ├── 更新设备状态为「在线」，失败计数清零
    │   │   ├── 检查 ACD 位（bit 5）
    │   │   │   ├── ACD=0 → 无告警，继续下一步
    │   │   │   └── ACD=1 → 紧接着发送 REQ_UD1（见告警采集流程）
    │   │   ├── 解析设备数据
    │   │   ├── 匹配已启用对象
    │   │   │   ├── 精确匹配成功 → 更新对象数值
    │   │   │   ├── 匹配到多条记录 → 不更新，展示 ⚠ 提示填写记录位置
    │   │   │   └── 无匹配对象 → 忽略该记录
    │   │   ├── 计算最终数值（经过线性函数计算后的值）
    │   │   └── 存储数据
    │   │
    │   └── 多次重试均失败 → 本次采集失败
    │       ├── 失败计数 +1
    │       ├── 如果连续采集失败次数 = 3
    │       │   └── 更新设备状态为「离线」或 保持保持「从未上线」
    │       └── 等待下个采集周期
```



**对象匹配规则：**

| 匹配结果 | 处理 |
|-|-|
| 记录位置已填写，DIB+VIB+记录位置精确匹配 | 匹配成功，计算并更新数值 |
| 记录位置未填写，DIB+VIB 匹配到唯一已启用对象 | 匹配成功，计算并更新数值 |
| 记录位置未填写，DIB+VIB 匹配到多条已启用对象 | 这些对象本次均不更新，保持上一值，对象名称旁展示 ⚠ 图标，hover 提示"该对象编码在设备中存在多条记录，请添加记录位置以便于成功采集数据。" |
| 帧中有记录但无对应已启用对象 | 忽略该记录 |
| 有已启用对象但帧中无匹配记录 | 该对象本次不更新，保持上一值 |



**异常处理：**

| 异常场景 | 采集行为 | 数值处理 | **设备状态影响** | 恢复方式 |
|-|-|-|-|-|
| 响应失败 | 本次采集失败，等待下个采集周期 | 保持上一值 | 失败计数+1；连续3次失败 → 离线 | 下个采集周期自动重试 |
| 帧中缺少对象匹配记录 | 该对象不更新 | 保持上一值 | 无影响（设备通信成功） | 用户检查 DIB/VIB/记录位置配置 |
| 多条记录匹配同一对象 | 该对象不更新 | 保持上一值 | 无影响（设备通信成功） | 用户填写记录位置以精确匹配 |
| 地址冲突（多台设备响应） | 本次采集失败，等待下个采集周期 | 保持上一值 | 保持原状态 + 记录告警 | 用户排查并解决地址冲突 |



##### 告警采集流程（Class 1）

Class 1 告警数据是表计上报厂商自定义告警信息的通道，具体告警类型取决于表计厂商的实现定义，M-Bus 标准不做统一规定。网关无法自主解析，需将原始值透传至数据转发模块，由上层应用系统或集成商负责解读。



**告警检测与采集时机**

网关在每台设备的 REQ_UD2 响应帧中，检查控制字段的 ACD 位（bit 5）：

| **ACD 值** | **含义** | **网关动作** |
|-|-|-|
| 0 | 设备无 Class 1 待读数据 | 无需处理 |
| 1 | 设备有 Class 1 告警数据待读取 | 紧接着对该设备发送 REQ_UD1 |

> ACD 是发现 Class 1 告警的唯一入口，无 ACD=1 则不发送 REQ_UD1。

采集时机规则：

- 每台设备的 REQ_UD2 响应完成后，若 ACD=1，紧接着对该设备发送一次 REQ_UD1，完成后继续总线上下一台设备的调度
- 每台设备每个采集间隔内最多触发一次 REQ_UD1；若本次 REQ_UD1 完成后 ACD 仍为 1，本间隔内不再重复采集
- REQ_UD1 的 FCB（帧计数位）与 REQ_UD2 独立维护，REQ_UD1 通信失败不影响 REQ_UD2 的 FCB 序列



**RSP_UD1 解析逻辑**

```Plain Text
网关发送 REQ_UD1 后，等待设备响应：

├── 设备返回无告警（E5h）
│   └── alarmState 更新为 "0x00"
│
├── 设备返回有告警（CI=0x71 + Alarm State）
│   └── alarmState 更新为实际告警值
│
└── 通信失败（超时/校验失败）
    └── alarmState 更新为 "0x00"，获取失败不确定是否有告警，默认无告警


REQ_UD1 的响应帧（RSP_UD1）结构如下（参见 M-Bus 官方文档 Fig. 34）：
┌──────┬───────┬───────┬──────┬──────────┬────────┬───────┬─────────────┬──────┬──────┐
│ 68h  │ 04h   │ 04h   │ 68h  │ C        │ A      │ CI    │ Alarm State │ CS   │ 16h  │
│ 起始 │ L     │ L     │ 起始 │ 控制字   │ 地址   │       │ 告警字节     │ 校验 │ 停止 │
│      │       │       │      │ (08h)    │        │ 71h   │ (1 byte)    │      │      │
└──────┴───────┴───────┴──────┴──────────┴────────┴───────┴─────────────┴──────┴──────┘
长度 L = 04h（C + A + CI + Alarm State，共 4 字节）
CI = 71h 表示这是告警响应帧
CI 之后仅有 1 字节 Alarm State，无 DIF/VIF 结构，无厂商 ID，无时间戳
若设备无告警，响应为单字节 E5h（确认帧）
```



**alarmState 与 Status 全局对象的关系**

`alarmState` 作为设备级状态信息，归属于数据转发服务全局对象中的 **Status 对象。**

- `alarmState` 无需用户手动配置对象，网关自动维护并随 `Status`对象一同上报（HTTP和MQTT数据转发服务需要新增Status全局对象，BACnet和Modbus当前已有Status全局对象）
- 用户在数据转发服务中勾选 Status 全局对象时，`alarmState` 自动包含在内



**异常处理**

| **异常场景** | **处理** |
|-|-|
| 表计不支持 Class 1（ACD 始终为 0） | `alarmState` 始终为 `"0x00"` |
| REQ_UD1 连续超时 | 不判定设备离线（Class 1 通道故障不影响 Class 2 采集）；`alarmState` 更新为 `"0x00"` |
| 其他异常导致无法解析RSP_UD1 | `alarmState` 更新为 `"0x00"`，获取失败不确定是否有告警，默认无告警 |

> **备注**：根据 M-Bus 标准，表计的 Class 1 告警为一次性告警，主站需要通过翻转 FCB 位发送第二次 REQ_UD1 来清除表计告警状态（表计返回 `E5h` 表示告警已清除）。具体 FCB 翻转时机和策略由研发评估。

### 数据转发

#### 功能定位

- **边界**：M-Bus设备采集数据通过HTTP、MQTT、BACnet Server、Modbus Server四种方式转发至客户的应用服务器或本地系统。M-Bus数据转发复用网关现有的数据转发模块框架，与其他协议设备（LoRaWAN、BACnet、Modbus、KNX、IO）的数据转发逻辑保持一致。
- **解决的痛点**：客户需要将M-Bus设备的计量数据（能量、流量、温度等）上报到云端平台进行集中监控和分析，或接入本地楼宇管理系统（BMS）/工业控制系统（SCADA）进行实时数据监控。



#### 设计决策

| 决策点 | 方案选择 | 理由 |
|-|-|-|
| 数据格式 | 复用非LoRa设备的MQTT/HTTP上报格式 | 保持与其他有线协议设备的一致性，降低开发和测试成本 |
| BACnet对象类型 | 数值对象映射为Analog-Input，字符串对象映射为CharacterString-Value | M-Bus设备数据只读，符合Input类型的语义 |
| Modbus寄存器类型 | 数值对象映射到Input Register，字符串对象映射到Holding Register | Input Register是只读寄存器，符合M-Bus数据只读的特性 |
| 单位处理 | MQTT/HTTP不需要单位字段，BACnet需要单位映射，Modbus不涉及单位 | BACnet对象有Units属性，Modbus寄存器没有单位属性 |
| 单位列表 | 采用符合BACnet标准或行业通用标准的工程单位 | 保持产品设计的一致性，用户在不同协议设备上看到相同的单位选项 |
| 地址/编号分配 | 网关自动分配，无需用户手动配置 | 简化用户操作，降低使用门槛 |
| 编号释放和复用 | 遵循网关现有逻辑 | 保持与其他协议对象管理逻辑的一致性 |



#### 功能概述

- **一句话描述**：M-Bus设备的采集数据通过HTTP、MQTT、BACnet Server、Modbus Server四种方式转发，数据格式与映射规则复用网关现有的数据转发框架。
- **典型操作路径**：

```
用户配置数据转发 → 添加转发服务（MQTT/HTTP/BACnet/Modbus）
→ 选择要转发的M-Bus设备对象 → 网关自动分配地址/编号 → 数据按配置的转发方式上报
```

##### BACnet映射规则

**数据类型定义**：

| 数据类型 | M-Bus DIF值 | 数据长度 | 映射为BACnet对象类型 |
|-|-|-|-|
| 整数 | 0x01-0x07 | 8/16/24/32/48/64位 | Analog-Input（数值对象） |
| 浮点 | 0x05 | 32位 | Analog-Input（数值对象） |
| BCD码 | 0x09-0x0C, 0x0E | 2/4/6/8/12位BCD | Analog-Input（数值对象） |
| 字符串 | 0x0D-0x0F | 可变长度 | CharacterString-Value（字符串对象） |

**映射原则**：

- M-Bus数据只读，所有对象映射到BACnet的Input类型
- 数值对象映射到Analog-Input，字符串对象映射到CharacterString-Value
- 网关自动为每个对象分配实例编号，无需用户手动配置
- Class 1的alarmStatus直接映射到Status全局对象

**映射表**：

| M-Bus数据类型 | BACnet对象类型 | 实例编号分配 | 单位映射 |
|-|-|-|-|
| 数值（整数/浮点/BCD） | Analog-Input | 网关自动分配，从0开始 | 根据M-Bus对象单位自动映射 |
| 字符串 | CharacterString-Value | 网关自动分配，从0开始 | 无单位属性 |

**单位映射规则**：

- **映射逻辑**：根据M-Bus对象的单位自动映射到对应的BACnet标准单位代码
- **特殊情况处理**：

  - 无单位：映射为no-units(95)
  - 未识别的单位：映射为no-units(95)

**实例编号分配规则**：

- 按BACnet对象类型分组（Analog-Input一组，CharacterString-Value一组）
- 每组从编号0开始分配
- 按对象添加顺序分配
- 当对象被移除时，对应的实例编号被释放，下次新增对象时优先使用已释放的编号

- 如果对应的 M-Bus 设备下有配置对象，展开设备可查看设备下已启用的对象信息，勾选对应需要添加的对象保存后，数据转发立即生效，网关将读取采集到的对象数据转发到对应的上层应用服务

  - **HTTP/MQTT 类型**：选择添加对象时的列表展示对象名称、对象ID、关联对象（M-Bus 没有关联对象逻辑，默认为-）

##### 转发失败处理

M-Bus 数据转发复用网关现有的转发失败处理机制。不同转发服务的失败处理逻辑不同：

- HTTP 转发服务：转发失败时，数据丢失
- MQTT 转发服务：转发失败时，如果有启用数据重传，则缓存数据等待重传，重传逻辑跟当前保持一致
- BACnet 转发服务：转发失败时，等待BACnet Client重新发起数据查询
- Modbus 转发服务：转发失败时，等待Modbus Client重新发起数据查询

### 本地自动化（Node-RED）

#### 功能定位

- **边界**：Device Input 和 Device Filter 节点支持 M-Bus 设备和对象信息，用户可基于 M-Bus 设备的采集数据构建本地自动化流程。
- **解决的痛点**：BMS 集成工程师需要基于 M-Bus 计量数据构建本地自动化流程（如当热量表读数超阈值时触发告警、当水表流量异常时发送通知）。



#### 设计决策

| 决策点 | 方案选择 | 理由 |
|-|-|-|
| 节点策略 | 扩展现有节点，不新建 M-Bus 专用节点 | 保持节点面板简洁，与现有协议体验一致 |
| 设备和对象同步 | 与设备管理页面取同一数据源 | 用户在设备页修改设备或对象名称后，Node-RED 自动同步，无需手动更新 |



#### 功能概述

- **一句话描述**：Device Input 和 Device Filter 节点支持 M-Bus 设备和对象信息，M-Bus 已启用对象的数据可被 Node-RED 流程消费。



#### 功能逻辑

##### **Device Input 节点**

Device Input 节点支持 M-Bus 设备，以及该设备下已启用的数据对象。

- 支持选择 M-Bus 设备
- 支持选择该设备下已启用采集的数据对象
- 输出消息格式与 MQTT 数据结构对齐
- 节点Help描述增加 M-Bus 信息，"This node outputs data from BACnet, Modbus, KNX, **M-Bus** and IO devices configured on the gateway GUI. To add new devices, please use the GUI."

---

##### **Device Filter 节点**

Device Filter 节点需要支持对 M-Bus 设备和对象进行筛选过滤。

- 支持按 M-Bus 设备 ID、设备名称、对象 ID进行筛选
- 筛选条件支持多个组合（AND / OR 逻辑）



#### 业务规则

- **数据依赖**：Node-RED 侧改动依赖 M-Bus 数据采集模块先完成，确保有数据源
- **实时同步**：设备或对象的名称修改后，Node-RED 中的配置自动同步，无需手动更新

### 设备库模板

#### 功能定位

- **边界**：基于 EG71 已有的自定义设备库功能，新增 M-Bus 设备模板的管理能力，包括手动添加、编辑、删除。通过预设设备模板，用户可在添加设备时引用模板初始化对象配置，提升批量部署同型号 M-Bus 设备的效率。
- **解决的痛点**：批量部署同型号 M-Bus 仪表时，需重复配置对象名称、DIB/VIB、单位等参数，缺乏标准化的对象配置模板，不同工程师配置不一致，设备对象配置无法复用，增加现场调试时间。

---

#### 设计决策

| 决策点 | 方案选择 | 理由 |
|-|-|-|
| 协议类型扩展 | 在现有自定义设备库基础上新增「M-Bus」选项 | 复用现有设备库框架，降低开发成本 |
| 对象配置字段 | 展示 DIB、VIB、单位、线性函数、记录位置等 M-Bus 特有字段 | M-Bus 协议原生标识，唯一确定一个数据记录 |
| 记录位置 | 隐藏到高级配置，DIB+VIB 重复时必填 | M-Bus 设备同一帧中可能存在多个 DIB+VIB 相同的记录，需通过序号区分 |
| BACnet/Modbus 转发 | 模板中可重新定义转发逻辑，设备使用模板进行对象初始化时以模板中对象定义的转发逻辑为准 | 给予用户灵活性 |
| 模板引用方式 | 手动添加设备时可选择引用模板，模板更新不影响已引用设备 | 保持设备配置独立性，避免模板变更导致设备配置意外变化 |

---

#### 功能概述

- **一句话描述**：在自定义设备库中新增 M-Bus 设备模板管理，支持手动添加、编辑、删除，用户可在添加设备时引用模板快速初始化对象配置。

- **唯一性校验**

  - 同一模板内，对象名称必须唯一
  - 同一模板内，DIB+VIB+记录位置的组合必须唯一

  | 校验场景 | 错误提示 |
  |-|-|
  | 对象名称重复 | 实时校验，重复时在对象名称文本框下提示"对象名称已存在"  <br/>保存时拦截 |
  | DIB+VIB 重复且未填写记录位置 | 失焦拦截，记录位置下方提示"该字段为必填项。"  <br/>~~保存时拦截，toast提示 "存在相同 DIB+VIB 的对象，请填写数据记录序号以区分"~~ |

- **DIB+VIB 重复处理**：

  - 允许同一模板内存在多个 DIB+VIB 相同的对象
  - 当 DIB+VIB 重复时，必须填写记录位置以区分不同记录

- 模板生效后出现在自定义设备库列表
- 展示设备型号、厂商、协议类型（M-Bus 标签）、对象数量、引用设备数（初始为 0）
- 后续可在手动添加设备时引用此模板初始化对象，或在新增自定义设备模板时引用

**对象编辑**

- 对象名称只读不可修改
- DIB、VIB、记录位置、单位、描述、线性函数可修改
- BACnet 转发配置可修改（默认折叠，勾选后展开），限制逻辑同 5.11.4.2 添加设备模板
- Modbus 转发配置可修改（默认折叠，勾选后展开），限制逻辑同 5.11.4.2 添加设备模板

  - **DIB+VIB 修改的级联影响**：
  
    - 修改 DIB 或 VIB 后，如果与模板内其他对象重复，必须同时修改记录位置
    - 修改记录位置后，如果与同 DIB+VIB 的其他对象重复，阻止保存
  
    | 校验场景 | 错误提示 |
    |-|-|

  - **删除对象的影响**：
  
    - 删除模板对象不影响已引用该模板的设备（设备对象已独立存储）
    - 删除对象前需二次确认

##### 删除设备模板

```Plain Text
自定义设备库列表 → 点击「删除」
  ↓
判断模板是否被设备引用
  ├─ 未被引用 → 二次确认弹窗 → 确认后删除
```

**删除校验**

- 判断模板是否被设备引用
- 引用关系在设备添加时建立（选择模板初始化对象）

**未被引用**

- 二次确认弹窗："确认要删除吗？"
- 确认后删除
