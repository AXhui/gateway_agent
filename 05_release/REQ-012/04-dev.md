## 3. 业务规则

### 3.1 入网成功判定（在线判定）

- **OTAA**：网关收到 Join Request 并下发 Join Accept 后，若在**节点超时时间内**收到正常上行数据包（**重复 Join Request 不计入有效数据包**），判定入网成功 → 状态**在线**。
- **ABP**：网关收到节点上行数据包且解析正常，即判定入网成功 → 状态**在线**。

### 3.2 入网失败判定

- **OTAA**：
  1. 收到 Join Request 但 **MIC 校验失败** → 判定**密钥错误** → 状态**入网失败**；
  2. 收到 Join Request 并下发 Join Accept 后，节点超时时间内**未收到有效上行数据包** → 判定**节点未收到入网包** → 状态**入网失败**。
- **ABP**：收到上行数据包但 **MIC 校验失败** → 判定**密钥错误** → 状态**入网失败**。

### 3.3 与 UG6x 的 5 条差异（原文照录）

1. EG71 OTAA 模式下没有「未收到JoinRequest」这个入网失败原因，不区分「未收到JoinRequest」和「从未上线」，因为 EG71 的超时时间较 UG6x 更长；
2. EG71 不单独将「密钥错误」和「节点未收到入网应答包」作为设备状态，使用统一「入网失败」状态，仅作为原因；
3. EG71 ABP 模式下没有「入网超时」，原因同 a；
4. EG71 超时时间为配置内的超时时间，不通过 Toolbox API 传入；
5. EG71 将新增的设备状态作为全局对象传给 BACnet 和 Modbus。

### 3.4 OTAA 默认密钥双 Key 校验流程（PRD §2.1.1，标注「当前已实现」）

选中默认 AppKey 时，NS 使用两套密钥入网验证：

1. **固定密钥**：`5572404c696e6b4c6f52613230313823`
2. **动态密钥**：由配置的 DevEUI + DevEUI 拼接生成（按字面为 16+16=32 位 hex 直接拼接；是否再做变换 PRD 未写，**待确认**）

处理流程：
1. 接收 JoinRequest 后，在完成所有密钥校验前**保留该报文**，不释放或丢弃；
2. **优先使用动态密钥**校验 MIC；
3. 动态失败 → 基于保留的报文**切换固定密钥再次校验**；
4. 两套均失败 → 入网失败，原因 Key 错误；
5. 任一成功 → 使用该套密钥生成 JoinAccept 并下发，设备以该密钥入网。

### 3.5 ABP 默认参数 · DevAddr 生成规则（PRD §2.2.1）

1. 截取用户配置的 DevEUI 中**第 10 至第 16 位字符**（示例：DevEUI `24e124136e445120` → 截取 `e445120`，为 7 位）；
2. 校验位 `*`：取 DevEUI 第 7 到 16 位（示例 `136e445120`），开头添加字符 `6`（→ `6136e445120`），按附录校验位算法生成 1 位校验位；
3. 步骤 1 的截取值拼接 1 位校验位，最终 DevAddr 格式 `[基础取值]*`（示例 `e445120*`，共 8 位）。

> **PRD 疑点**：步骤 3 写「截取的 6 位字符」与步骤 1 的「第 10 至 16 位」（7 位，示例也是 7 位）矛盾；按示例与 DevAddr 8 位长度推断应为 **7 位 + 1 校验位 = 8 位**，步骤 3 的「6位」疑为笔误。**待产品确认。**

校验位算法（PRD 附录 4.1 `GenerateSNCheckBit`，参数摘要）：字符映射表 encryptString = `ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789` → decryptString = `29*xy+ab57c4d3efg6hijk81lm@%^rz!n.-#`；追加 keyForCode = `YEASTAR` 参与映射；checkBit 初值 `0x12`；偶数索引字节累加（ADD_NUMBER=1）、奇数索引字节递减（SUB_NUMBER=2，跳过 0 值）；结果四字节折叠求和后 `mod 10 + 0x30` 得 1 位 ASCII 数字。完整代码见 PRD 附录 4.1。

### 3.6 ABP 默认参数 · 会话密钥生成规则（PRD §2.2.2）

NwkSKey 与 AppSKey 生成规则与 OTAA AppKey 规则一致，**两套密钥同类型生效**（同时用固定或同时用动态）：

1. 固定密钥：`5572404c696e6b4c6f52613230313823`；
2. 动态密钥：DevEUI + DevEUI 拼接。

> **PRD 疑点**：固定密钥只给了一个值、动态规则只给了一种推导，NwkSKey 与 AppSKey 的**取值是否彼此相同**（同值）或各有推导盐 PRD 未写明。**待产品确认。**

### 3.7 ABP 默认参数 · 数据收发校验流程（PRD §2.2.3）

1. **预配置**：用户输入 DevEUI 后，系统自动生成唯一且固定的 DevAddr + 两套会话密钥（按 §3.5/§3.6）；
2. **首次上行校验**：NS 收到该 DevAddr 上行包 → 先动态密钥校验 MIC → 失败则固定密钥再校验 → 均失败返回入网失败（原因 Key 错误）；任一成功 → **持久化保留该套成功密钥并绑定至该 DevAddr**；
3. **后续上行**：直接使用已绑定的成功密钥校验 MIC，不再重复尝试两套；
4. **下行加密**：向该 DevAddr 下发下行数据必须使用已绑定的那套密钥加密，确保上下行密钥一致。

### 3.8 编辑页切换配置文件/型号的三场景值规则（PRD §2.1.2）

前提：OTAA 字段 = AppKey（必填可编辑）+ DevAddr/AppSKey/NwkSKey（不可编辑，入网后自动填充）；ABP 字段 = DevAddr/AppSKey/NwkSKey（必填可编辑），无 AppKey。

| 场景 | 操作 | 默认/自定义状态 | 字段值 |
|---|---|---|---|
| 1 同类型切换 | 切换设备型号（含 None）、或切换配置文件但激活类型不变（OTAA→OTAA、ABP→ABP） | 保持不变 | 保持不变 |
| 2 ABP→OTAA | 切换为 OTAA | 保持不变 | AppKey：空（ABP 无此字段）、必填；DevAddr/AppSKey/NwkSKey：从 ABP 配置带入（ABP 必有值），不可编辑 |
| 3 OTAA→ABP | 切换为 ABP | 保持不变 | DevAddr/AppSKey/NwkSKey：从 OTAA 入网数据带入（已成功入网则有值，否则为空），可编辑；AppKey：不显示 |

### 3.9 编辑页前端暂存逻辑（PRD §2.1.2）

- 未点保存时切换配置文件类型：所有字段值**前端暂存**；
- 切回原类型：**恢复暂存值**；
- 一旦保存：**未激活类型的字段值被清除**，再切回时为空、需重新填写。

### 3.10 Milesight 设备判定

满足其一即 Milesight 设备：① 设备型号选择为 Milesight 设备；② DevEUI 以 `24E124` 开头（oui 匹配）。判定结果驱动激活设置单选默认值（见 03-ued.md §6.3）。

### 3.11 历史数据兼容（ABP，PRD §2.3.1-4）

旧设备升级至本版本：保留 Device Address 原有配置值不变，且该配置项自动标记为「自定义值」（activationMode = custom）。

### 3.12 编辑权限控制（ABP，PRD §2.3.1）

- 「默认值」：置灰不可编辑 = Device Address / Network Session Key / Application Session Key；保留可编辑 = Uplink Frame-counter、Downlink Frame-counter、Timeout；
- 「自定义值」：所有配置项保留原有编辑权限，无额外置灰。

### 3.13 扫描 · 设备过滤与去重（PRD §3.2-1）

1. 收到 Join Request → **优先检索本地数据库**：该 DevEUI 已存在于当前网关设备列表 → **直接忽略该报文**；
2. 该 DevEUI 已存在于扫描确认池 → **更新**其信号强度（RSSI/SNR）与更新时间（不新增行；已忽略设备同样正常更新）。

### 3.14 扫描 · MIC 匹配（PRD §3.2-2）

- 提取报文中 DevEUI、AppNonce 等信息，用扫描配置页定义的 **AppKey 列表（含勾选的 Milesight 默认 Key 两套）**逐一匹配；
- 匹配顺序：**从上至下**；
- 校验成功：判定合法可接入，立即将 DevEUI、RSSI、SNR、最后更新时间写入确认池，并**记录保存匹配成功的 AppKey**；
- 全部失败：视为非法或非目标设备，**不予记录**。

### 3.15 静默扫描原则（PRD §3.2-3，红线）

扫描模式下，**即便 MIC 校验成功，网关也严禁向设备发送 Join Accept**。仅用户确认添加入设备列表的设备才发送 Join Accept。

### 3.16 设备型号识别规则（PRD §3.1.2-1）

- 系统通过 DevEUI 识别设备型号 → 自动填充；
- 匹配到多个：**内置设备库型号 > 自定义设备型号 > 自定义设备型号 ID 靠后的设备**；
- 内置库型号重复 → 显示多个（如 AM102/AM102L/AM103/AM103L）；
- 无法识别 → None。

### 3.17 添加设备提交逻辑（PRD §3.1.2-3）

- 确认后批量注册所选设备至当前网关，**默认添加全部对象**；
- **没有设备型号（None）的设备：不添加对象**（设备本身仍注册，字面理解，待确认）；
- 成功：提示「xx个设备添加成功」+ 刷新当前页 + 已添加设备从扫描确认页移除；
- 冲突（多用户抢先添加）：不强制拦截，提交时提示「xx个设备已存在」，其余非冲突设备正常添加。

### 3.18 数量上限（PRD §3.1.2-1）

- 扫描确认池列表上限 **2000**：超出覆盖更新时间最久的设备；
- 勾选设备数 > 2000：提示超过设备上限；
- 对象总数 > 20000：提示超过对象上限（「对象」= 设备的数据点/功能对象，精确口径待确认）。

### 3.19 配置持久化与备份

- 扫描 AppKey 配置属网关配置：**升级后保留**，**需支持备份还原**；
- 扫描确认页中的设备**不包含在备份文件中**。

### 3.20 扫描中重进配置页（PRD §3.1.1）

- 允许新增/删除 AppKey；
- 已扫描到的设备及其匹配的 AppKey **保留**（即使该 AppKey 已在配置页被删除）；
- 【开始扫描】按钮变更为【应用】。
- （新增 Key 是否即时参与正在进行的 MIC 匹配 PRD 未明说，按「应用即生效」理解，**待确认**。）

### 3.21 全局提示条（PRD §3.1.1）

- 扫描中所有页面（含状态页）显示「正在LoRaWAN扫描中」；
- 扫描到新设备 → 红点 + 设备数（= 确认池中未被添加的节点数）；
- 点击 → 跳转扫描确认页，**不中断扫描**，去红点变灰、保留设备数。

### 3.22 导入文件规则（PRD §3.1.1）

- 类型：csv / xlsx（浏览器文件选择弹窗限制类型）；
- 解析：检索表头为 AppKey 的列（大小写不敏感），列内容为合法 AppKey（32 位 hex，大小写不敏感）即导入成功；
- 大小 ≤1M；文件内有效 Key 数 + 已存在 Key 数 ≤1000；
- 存在任一非法 AppKey → **全部失败**（不部分导入）；
- 合法 Key 重复 → **不去重**，允许重复。

## 4. 表单校验规则

| 字段 | 必填 | 格式 | 长度/数量 | 唯一性 |
|---|---|---|---|---|
