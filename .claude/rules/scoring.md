# 评分规则 · Scoring（五维评分机制 + 三角色验收）

> **适用范围**：一切 `05_release/REQ-###/` demo 的五维评分（`quality.json`）、同步质量门槛的分数来源。
> **性质**：硬性约束。**分数必须经三角色验收（DEV / UED / TEST）产出证据后按本文件扣分表落定**；无证据的印象分一律无效，退回重评。
> **关联**：AGENTS.md「核心规则：生成 demo 后必须自动提交」（流程入口）、`.claude/knowledge/K_validation.md`（R1–R5 证据源）、`tools/score_component.py`（component 维脚本权威）、`tools/sync_demo_to_feishu.py`（80 分门槛）。

---

## 0. 三角色验收协议（评分前置门，硬性）

**背景**：存量 quality.json 曾出现两类失真——①分数集中在 84~95 且无 `reason`（REQ-013~016），无从追溯；②AI 自评既当运动员又当裁判。本协议要求：**demo 生成后、写 quality.json 前，依次以 DEV / UED / TEST 三个角色视角各走查一遍**，每角色按自己的清单产出扣分证据，分数由证据反推得出。角色是**视角**不是人：可由同一 agent 依次切换扮演，也可分派给对应链路 agent（ued-a5 / dev / test-t*），关键是三份清单各走一遍、证据分行落盘。

### 0.1 角色与维度归属

| 角色 | 验收视角 | 主责维度 | 证据来源 |
|---|---|---|---|
| **UED** | 信息架构、视觉基准、红线令牌 | structure、visual | §4.① §4.④ 扣分表 |
| **DEV** | 组件契约、装配实现、令牌引用 | component（脚本佐证） | score_component.py `--report` 明细 |
| **TEST** | 交互链完整性、状态机、字段校验 | interaction、field | §4.③ §4.⑤ 扣分表 |

### 0.3 证据落盘（validation.md「三角色验收」节）

每条证据一行，格式固定：

```
[角色-序号] 位置｜条款｜现象｜建议扣分
例：[U3-2] demo.html:1421｜spacing §4 字号集合｜出现 13px 辅助文字｜-4
例：[T2-1] 告警列表区块｜interaction-completeness §1.1 列表类｜缺空态（ms-empty）｜-10
```

- 位置写 `file:line`、DOM 选择器或区块名，必须可定位复核。
- `score_component.json`（`--report` 产物）整体作为 DEV 证据归档，不逐条手抄。
- **证据行是扣分的唯一依据**：无证据不得扣分；有证据不得漏扣。

### 0.4 落分与真实性校验（对不上 = 无效评分）

1. structure / interaction / visual / field 四维：**分数 = 100 − Σ(该维归属证据行的建议扣分)**，向下取整，单维封底 0。
2. component 维：直接采用脚本分（`--write` 覆盖），其证据即 `score_component.json`，不手工反推。
3. **真实性校验（落分后必做）**：逐维核对 quality.json 分数能否由 validation.md 证据行（+ component 脚本分）反推得出；**任一维度对不上 → 评分无效，退回重评**。
4. 模块缺失类（structure）合计封顶 −40，防单维炸穿综合分；封顶规则在 validation.md 注明。

### 0.5 时序（嵌入 AGENTS.md 核心规则）

```
demo.html 生成
→ prompt.md（原始提示词）
→ 三角色验收（本节 §0.2 清单 → §0.3 证据落盘）
→ 按扣分表落分（§0.4）→ quality.json + reason（§5 模板）
→ score_component.py --write（component 脚本覆盖）
→ 真实性校验（§0.4.3）
→ 综合 ≥80 门槛 → 同步飞书 → commit
```

## 1. 设计原则

1. **扣分制，不做印象制**：每维 100 起步、逐项扣分，每条扣分落到「条款 + 位置」证据。可复核、可回归；UED 改分时能对账。
2. **一维一职权（归责矩阵）**：同一问题只在一个维度扣一次分，杜绝双计（见 §2）。
3. **基准分级**：评分永远有明确对标物——一级 Figma 真源（有设计稿时）；二级 PRD 结构 / 字段描述；三级组件库契约 + tokens + 规则红线（无设计稿时，库与规则即「正确」）。不存在「凭感觉像不像」。
4. **demo 不替 PRD 背锅**：PRD 自身矛盾（C2）/ 隐含大缺口（D 大）导致无法实现的部分**不扣 demo 分**，走台账 + 评论回流（interaction-completeness §2.5）。分数只衡量 demo 对基准的还原，不衡量 PRD 质量。

## 2. 归责矩阵（防重复扣分）

| 问题现象 | 归属维度 | 依据条款 |
|---|---|---|
| 自造 class / 未注册类 / 手写渲染函数 / 裸色值裸间距**比例** | component | score_component ①②③⑤ |
| 令牌**越红线**（间距阶梯 / 字号集合 / 图标尺寸越界） | visual | spacing §1 §3 §4 |
| 模块整体缺失 / 多出 / 编排错序 | structure | R4 + 装配计划 |
| 模块内部交互链断（loading / error / empty / 确认缺） | interaction | interaction-completeness §1 |
| 模块内部字段缺漏 / 类型错 / 校验缺 | field | PRD 字段表 + D4 |
| 私造壳 / 私加菜单（**入口归属**判错） | structure | AGENTS.md 壳契约 |
| 未调 `MS_EG71_SHELL`（**调用方式**缺 render/bind） | component | score_component ④ |
| 可见 UI 出现评审注记等非产品内容 | visual | page-assembly §5 |

> 裸值比例（component 规则⑤统计口径）与越红线（visual 人工判定口径）允许轻度交叉：前者是代码统计的自动近似，后者是对呈现结果的判定，双保险不视为双计。

## 3. 通用模型

**分档锚点**（五维共用，与综合 80 门槛对齐）：

| 分数段 | 判定 | 动作 |
|---|---|---|
| 90–100 | 基准内，轻微瑕疵 ≤2 处 | 入表，UED 抽查 |
| 80–89 | 轻微瑕疵 3–5 处，不影响理解 | 入表 |
| 60–79 | 实质缺陷，局部需返工 | 修完重评，不入表 |
| <60 | 结构性错误 | 退回重做 |

**综合权重口径**（`sync_demo_to_feishu.py` 已实现）：交互 0.25 最高——交互链断则 demo 丧失「可点击 PRD」核心价值；结构 / 组件 / 视觉各 0.2——骨架 / 零件 / 皮；字段 0.15——机械可比对、后期易补。

## 4. 五维扣分表

### ① structure 结构还原度 —— 搭得对不对（UED 主责）

**评什么**：路由与壳入口、模块清单、编排顺序、栅格层级、页面类型形态。
**不管**：模块内部长什么样（component / visual）、模块内交互（interaction）、字段（field）。

| 违规项 | 扣分 | 条款 |
|---|---|---|
| 装配计划 / PRD 模块整体缺失 | −15/个 | R4 |
| PRD 没有的整块功能多出 | −10/个 | 结构对标 |
| 模块编排顺序与基准不符 | −5/处 | 装配计划 |
| 未走唯一壳 / 私造壳 / 私自加菜单 | −20 | AGENTS.md 壳契约 |
| 页面类型卡片形态错（列表页套多卡片等） | −8 | 壳契约第 3 条 |
| 区块分节间距 / 栅格层级明显错乱 | −5/处 | spacing §1 |
| 标题层级跳级（H1→H3 相邻） | −8 | spacing §4 |

模块缺失类（前两项）合计封顶 −40。

### ② component 组件类型还原度 —— 用没用对零件（DEV 主责，脚本权威）

**机制**：`score_component.py --write` 脚本分直接生效，AI 自评一律被覆盖。脚本 5 规则：

| 脚本规则 | 权重 | 评什么 |
|---|---|---|
| ① 组件库命中率 | 20% | `bc-*` / `ms-*` 占全部 class 比例，自造类越多分越低 |
| ② 注册表覆盖 | 20% | 用到的类是否在 library / assets 真源注册 |
| ③ 契约调用 | 25% | `MS_BIZ_INDEX[id].render` 调用数；手写渲染函数 −15/个（R2b 脚本近似） |
| ④ 壳契约 | 15% | `MS_EG71_SHELL.render + bind`；私有壳结构类 −20 |
| ⑤ 设计令牌 | 20% | `var(--*)` vs 裸值比例 |

追加约束：
- reason 必须摘录脚本扣分明细前 3 条（引 `score_component.json`）。
- **已知边界**：规则④按 EG71 硬编码，cctv / cv / router 线无统一壳会被系统性重扣——非 EG71 线分数照出，reason 注明「规则④待扩展」，不误导读表人。
- 脚本分与修复后自评分差 >15 → 说明组件实现与规则不符，先修 demo 再同步。

### ③ interaction 交互逻辑还原度 —— 动起来对不对（TEST 主责）

**评什么**：每个 PRD 功能点的交互链五段（入口→操作→反馈→结果态→边界）是否完整、行为方向是否与 PRD 一致。

| 违规项 | 扣分 | 条款 |
|---|---|---|
| B 类断链未补全（loading / error / empty / 确认缺） | −10/处 | interaction-completeness §1.1 |
| 危险操作无确认弹窗 | −10/处 | 必备状态集 |
| 交互行为与 PRD 流程相反 / 走不通 | −15/处 | C2 判定口径 |
| 开关 / 启停无切换反馈或无失败回滚 | −8/处 | interaction-completeness §1.1 |
| 启停状态保持违规（禁用后重置值） | −8/处 | business-specific §6.2 |
| 空态 / 加载态未用 `ms-empty` 等库组件 | −5/处 | 组件契约 |
| 键盘可达性缺失（Esc 关弹窗 / focus 圈） | −3/处 | 五轴交互 |

**免责条款**：C2 / D 大缺口（PRD 矛盾或未定义且涉业务规则）demo 按字面占位实现的，**不扣分**——归台账走评论回流。

### ④ visual 视觉还原度 —— 看起来对不对（UED 主责）

**评什么**：呈现结果与视觉基准的偏差 + 红线令牌越界。

| 违规项 | 扣分 | 条款 |
|---|---|---|
| 可见 UI 出现非产品内容（纯净性） | −15/处 | page-assembly §5（修复后重评） |
| 主色 / 语义色用错 | −6/处 | tokens.css |
| 标题规格 / 层级不符（EG71 走 `B_ComTitle` 两变体） | −6/处 | 标题契约 |
| Tab 栏 / Alert 位置不符 | −6/处 | Tab / Alert 契约 |
| 图标未走 S_Icon / 同组不同尺寸 / 越 16–44 阶梯 | −6/处 | spacing §3 |
| 间距 / 字号越红线（非阶梯值、13px 等） | −4/处 | spacing §1 §4 |
| 对标 Figma 实测偏差（色值明显差 / 间距档位差） | −3/处 | 基准一级 |
| runtime 已知偏差未按 spacing §7 清单就地修正 | −4/处 | spacing §7 + assembly-integrity |

### ⑤ field 字段还原度 —— 内容对不对（TEST 主责）

**评什么**：PRD 定义的数据字段在 demo 的还原——清单、类型、默认值、校验、枚举、文案、单位。

| 违规项 | 扣分 | 条款 |
|---|---|---|
| PRD 明确定义的字段缺失 | −8/个 | 字段还原本义 |
| 字段控件选型与语义不符（枚举用输入框） | −5/个 | K_mapping |
| 校验规则缺失 / 错误（必填 / 格式 / 长度 / 范围） | −5/条 | D4 |
| 默认值与 PRD 不符 | −4/个 | PRD |
| 枚举选项缺漏 / 文案与 PRD 不一致 | −4/项 | PRD |
| 单位 / 格式化错误（大小写、进位、时区） | −4/处 | IoT 领域约定 |
| PRD 矛盾处未按已裁决侧实现 | −5/处 | C2 |

**免责条款**：D 类 demo 补的合理默认字段不扣不奖——基准是「PRD 写了的必须对」，不是「PRD 没写的不许有」。

## 5. reason 与证据规范（硬模板）

- `quality.json` 的 `reason` 每维一行，格式：`维度 分数：扣分点 = 条款 × 处数（证据行号）`；无扣分写「零扣分」。
- 示例：
  > `structure 85：−15 PRD 模块缺失×1（U2-1 告警规则模块未落地）；visual 96：−4 字号越红线×1（U3-2 13px 辅助文字）；component 92：脚本分，③手写渲染函数 1 个（score_component.json）；interaction 90：−10 空态缺失×1（T2-1）；field 100：零扣分（T4 全对）`
- 明细证据落 `validation.md`「三角色验收」节；quality.json 只放分数 + 摘要。
- **缺 `reason` = 违规**（存量 REQ-013~016 即此问题），同步前必补。

## 6. 与既有机制挂钩

| 机制 | 关系 |
|---|---|
| R1–R5（K_validation） | 本文件的证据源：R4→structure、R2b→component、R5 / 缺口清单→interaction、R1 / 红线→visual |
| score_component.py | component 维唯一权威，`--write` 覆盖 + `--report` 作 DEV 证据 |
| 80 分综合门槛（sync_demo_to_feishu.py） | 分数真实性由 §0.4 反推校验保障，门槛拦截低质入表 |
| UED 复核（飞书表格「校验状态」） | UED 改分与 AI 分差 >10 的维度，把判例回写本文件 §4 补锚点案例——评分标准随复核进化 |

## 7. 边界

- 本文件管「demo 五维评分怎么打、怎么验」；demo 怎么拼装归 page-assembly.md，发布流程归 release.md。
- `output/` 下的临时校验页不触发本评分（不进 `05_release/` 即不入表）。
- 非 PRD 驱动的纯组件页无「PRD 字段表」基准时，field 维以组件 SKILL.md 契约字段为基准。
- 扣分值调档（−4 / −8 / −15 一档）由 UED 复核判例沉淀驱动修订，修订即 bump 本文件。
