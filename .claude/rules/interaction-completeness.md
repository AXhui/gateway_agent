# 交互链完整性与 PRD 反馈闭环 · Interaction Completeness & PRD Feedback Loop

> **适用范围**：一切按 PRD 生成的 demo——A4 渲染（补全交互链）、A5 校验（缺口判定 + 差异核对）、A6 反馈（多维表格 issue 台账全量登记 + PRD 评论只发需求侧逻辑漏洞）。
> **性质**：硬性约束。demo 不允许只渲染 PRD 字面写到的「正向路径」；PRD 有缺口时 demo 补全链路，其中**需求侧逻辑漏洞**（§2.5 判定）反向评论回 PRD 文档，形成「PRD → demo → 校对 → PRD」闭环。
> **与既有文档的关系**：`page-assembly.md` 管 demo 怎么拼（L3 装配 + 纯净性），本文件管 demo 拼完后**链路是否完整**以及**缺口如何回流 PRD**；`K_validation.md` 的 R5 / 纯净性校验挂钩本文件。

## 1. 交互链完整性红线（A4 渲染时执行）

**每个 PRD 功能点必须落成完整交互链**：

```
入口（怎么触达）→ 操作（点/输/选）→ 即时反馈（loading/校验）→ 结果态（成功 / 失败 / 空 / 边界）
```

1. **必备状态集**（按功能点裁剪，逐项核对）：
   | 功能点类型 | 必备状态 |
   |---|---|
   | 列表/表格 | 加载中 / 空态 / 数据态 /（涉及删除时的）危险确认 |
   | 表单 | 未填默认态 / 校验失败态 / 提交中 / 提交成功反馈 |
   | 操作按钮 | 默认 / hover / loading（异步时）/ 危险操作的确认弹窗（`B_Eg71Modal` / `B_ComDangerAction`） |
   | 开关/启停 | 切换反馈 + 失败回滚提示 |
   | 数据同步/下发 | 进行中 / 成功 / 超时失败 |

2. **PRD 未写但链路必需的状态：允许且必须补全**——用资产库既有组件补（映射清单标注 `【PRD 缺省 · demo 补全】`），补全原因与形态记入 `validation.md`，**不进可见 UI**（纯净性不变，page-assembly.md §5）。
3. **补全边界（判断红线）**：只补**链路必需态**（loading / error / empty / 确认），**不发明 PRD 没有的功能、入口、业务规则**。PRD 写「A 功能」而你觉得 A 缺一个业务能力（如缺权限分支、缺失败后的业务去向）→ 那不是补全项，是 §2 的 C/D 类缺口，走评论回流，demo 不擅自实现。

## 2. 缺口分类（A5 校验时逐功能点产出）

| 类别 | 判定 | demo 处理 | 台账 | PRD 评论 |
|---|---|---|---|---|
| **A 完整** | 链路五态齐 | 无 | 无 | 无 |
| **B 链路断** | 缺 loading / error / empty / 确认等必要状态 | demo 补全（§1.2） | 记 | **不发**——状态链补齐是 demo 职责；若该状态的行为本身缺业务规则（如「失败后是否自动重试」没写），升级按 D 大缺口处理 |
| **C 描述不完整/矛盾** | PRD 对某状态的行为没写或两处冲突 | demo 按 PRD 字面实现，缺的状态用最小合理默认 | 记 | 拆半：**C1 UI 级**（排序/入口形态/措辞，任一实现都不影响业务正确性）→ 不发；**C2 逻辑**（两处矛盾须裁决 / 流程断头）→ 发方案评论 |
| **D 隐含缺失** | PRD 没提但产品上必需（权限、边界值、失败业务去向） | 小缺口（纯 UI 态）→ 补全；大缺口（涉业务规则）→ **不实现**，占位为 PRD 字面形态 | 记 | 小缺口不发；**大缺口 → 发方案评论** |

- 缺口清单落在 `05_release/REQ-###/validation.md` 专节「交互链缺口（A5）」，每条含：功能点 / 类别 / 缺什么 / demo 处理 / **差异归因（§2.5）**；归因为逻辑漏洞的条目另附**方案建议**。
- **断链（B 类）未补全即校验不过，退回 A4**；缺口存在但未记 issue → A5 视为校验未完成。

## 2.5 交互×需求差异核对（评论过滤门，A5 产出）

**缺口清单 ≠ 评论清单。** A5 产出缺口清单后，逐条做差异核对——把「demo 交互」与「PRD 需求」的差异归因到一侧，**只有「需求侧逻辑漏洞」才进 PRD 评论，UI 实现细节一律不上 PRD 文档**（只落 validation.md + 台账）。

### 差异核对表（validation.md 专节内，逐条一行）

| 功能点 | PRD 写了什么（原文摘录；矛盾时两侧都摘） | demo 实现了什么 | 差异归因 |
|---|---|---|---|
| （示例）Relay ID 位数 | 正文「8 位十六进制」；图例 `24E124FFFE123456` 为 16 位 | 按图例 16 位展示 | **需求侧逻辑漏洞**（前后矛盾） |
| （示例）组网方式选项排序 | 表格未定义排序 | 按 LoRa Mesh / IP / IP & Mesh 排序 | demo 侧 UI 细节（不发） |

### 归因判定口径

**需求侧逻辑漏洞（发方案评论）**——差异源于 **PRD 自身逻辑站不住**，任一实现都无法自洽：

1. **前后矛盾**：PRD 内部两处描述冲突（正文 vs 图例、表 vs 文、附录 vs 正文），实现时只能取其一；
2. **流程断头**：链路定义走不通——成功/失败后的去向未定义、跳转目标不存在或不在本需求定义范围、两个状态互斥却被要求并存；
3. **业务规则空白**：影响功能正确性的规则未定义——位数 / 格式 / 枚举值 / 默认值 / 权限分支，且不同取值会产生不同业务行为。

**demo 侧 UI 细节（不发评论）**——差异源于 **demo 的实现选择**，任一合理实现都不影响业务正确性：

1. 展示态补全（loading / empty / 确认弹窗等 B 类链路状态）；
2. 纯 UI 形态选择（入口放卡片还是行、选项排序、分组方式、文案措辞、与组件库契约的对齐选择）；
3. PRD 范围外的功能增补构想（「建议加 XX」类产品想象）。

**一句话判定**：这条评论是在指出「PRD 自己的逻辑有洞」（发），还是在告诉作者「demo 帮你补了个实现细节」（不发）？后者是 demo 的工作汇报，不是对 PRD 的评审。

**方案门槛（发评论的硬性要求）**：逻辑漏洞评论必须带**可拍板的方案**——写明建议裁决取哪一侧 / 建议补什么规则 / 建议默认值，让 PRD 作者回复「同意」即可闭环；只提问不给方案的评论不合格，A6 退回重写。

## 3. issue 台账（多维表格驱动，全量登记）

每条 B/C/D 缺口在多维表格 **「PRD 反馈台账」** 表登记一行（A6 执行，通道：`lark-cli base +record-batch-create`，scope 已授权）。**台账是完整台账，不随评论口径收窄**——不发评论的行也照记，只是评论状态标「不发」：

| 字段 | 内容 |
|---|---|
| REQ | `REQ-###` |
| 功能点 | PRD 中的功能名（如「M-Bus 协议下发」） |
| 类别 | B 链路断 / C 待澄清 / D 建议增补 |
| 差异归因 | 需求侧逻辑漏洞 / demo 侧 UI 细节（§2.5 判定口径） |
| 缺口描述 | 一句话（demo 侧视角） |
| demo 处理 | 已补全（形态）/ 按字面实现 / 未实现-待 PRD |
| PRD 文档链接 | 原始飞书文档 URL |
| PRD 评论状态 | 未评论 / 已评论 / 已解决 / **不发-非逻辑漏洞** |
| 评论链接 | `drive +add-comment` 返回的 comment URL |
| demo 版本 | commit short sha |

台账表 URL 的唯一配置源：`tools/feishu_issue_table.txt`（一行 URL；**未配置 = 降级模式**：A6 整体跳过台账写入与 PRD 评论回写，仅在报告警告，不阻断质量记录主流程）。

## 4. PRD 评论回写（A6 执行，仅逻辑漏洞）

**只对 §2.5 差异核对归因为「需求侧逻辑漏洞」的条目**（C2 / D 大缺口）向 **PRD 原始飞书文档** 发评论；其余行台账状态置「不发-非逻辑漏洞」，不进 PRD 文档。评论是**方案评论**：指出漏洞 + 给出可采纳的方案，不做 UI 层泛泛点评。

```bash
lark-cli drive +add-comment \
  --doc "<PRD 飞书 URL，取自 REQ 目录 meta 或 issue 行>" \
  --content '<评论正文>' \
  --as user
```

- **评论正文模板**（方案评论，固定结构，可整体复制改写）：
  > 【UED 反馈 · REQ-###】功能点「X」：需求逻辑漏洞——<PRD 原文矛盾两侧 / 流程断头点 / 业务规则空白>。方案建议：<可直接采纳的裁决（取哪一侧）/ 补充规则 / 建议默认值>。Demo 处理：<demo 当前按哪一侧实现>。Demo 预览：<链接>。
- 评论成功后把 comment 链接回填台账行（`+record-batch-update`），状态置「已评论」。
- PRD 文档链接的记录约定：PRD 从飞书拉取（`tools/fetch_feishu_doc.py`）时，源 URL **必须**存入 `00_raw` / REQ 目录的 `source.txt`（一行 URL）；没有源链接的 REQ，A6 跳过评论并在报告标注「PRD 非飞书源，评论未发」。
- **发送门禁**：评论以登录用户身份公开发到协作文档——每批发送前 A6 在会话里展示评论清单（功能点 + 正文），确认后批量发送；同 REQ 后续增量缺口可直接发。
- **不合格评论退回**：正文只有提问没有方案建议、或内容属 UI 实现细节（§2.5 不发清单）的评论，发送前剔除并退回 A5 重写归因。

## 5. 校验挂钩

| 规则 | 拦截的违规 | 对应条款 |
|---|---|---|
| R5 交互链完整性 | 功能点断链未补全（B 类裸奔）；必备状态集缺失 | §1 |
| 纯净性 | 补全标注（「PRD 缺省 · demo 补全」）出现在可见 UI | §1.2 |
| R4 结构覆盖 | PRD 功能点未逐条进入交互链清单 | §1 |
| 评论口径 | 缺口清单未做差异归因；UI 细节类差异发上 PRD 评论；逻辑漏洞评论无方案建议 | §2.5 / §4 |

## 6. 边界

- 评论是**反馈**不是**改稿**：PRD 是否采纳由 PRD 作者决定，demo 侧只在台账跟踪状态（已评论 → 已解决），不代写 PRD。
- **差异核对只决定「谁被评论」**，不改变 demo 的补全/占位行为：B 类该补照样补、D 大缺口该占位照样占位（§1 / §2 的 demo 处理列不变），不发评论 ≠ 不处理。
- 多维表格台账与既有「UI Demo 记录」表（`tools/sync_demo_to_feishu.py` webhook 通道）是两张表两件事：前者按缺口记行（本文件），后者按 demo 记行（release 流程），不得混写。
- 非 PRD 驱动的纯组件校验页（`output/`）不触发本闭环。
